# Luanti 服务端实体规模实测（原始证据）

日期：2026-10-27。机器：本机 Ubuntu，14 GiB RAM，`MemAvailable` 约 6.7 GiB，无 swap 变动。
被测：`Luanti 5.10.0 (Linux)`，LuaJIT 2.1，`luantiserver`，`--gameid minetest_game`，`mg_name = singlenode`，`dedicated_server_step = 0.09`（**实时基准 = 11.1 step/s**），`max_forceloaded_blocks = -1`。

判定口径：`steps_per_sec` 由 globalstep 计数/墙钟得到，跌破 11.1 即为服务端跟不上实时。
所有配置**顺序执行**，同一时刻只跑一个服务端。原始日志行按运行顺序逐字粘贴，未改写数字。

## 2. 实体生命周期：无玩家场景必须先 emerge 再生成

这是本轮最重要的工程发现，也是最容易静默出错的地方。

### 2.1 同一 server step 内 forceload + add_entity → 实体全部丢失

```
14:45:03  BENCH spawn count=1000 mode=idle forceload=16/16 cols=32 extent=62
14:45:05  BENCH sample count=1000 mode=idle entities=0 stepped=0 steps_per_sec=11.06
...
14:50:15  BENCH forceload count=1000 mode=idle ok=16/16 cols=32 extent=62
14:50:16  BENCH spawn count=1000 mode=idle failed=0        ← add_entity 全部“成功”
14:50:18  BENCH sample count=1000 mode=idle entities=0     ← 但一个都不在了
```

### 2.2 分开 tick 也不够：与 emerge 完成时刻存在竞态

同一份代码，只改 forceload / add_entity 的时刻（秒），各跑一次：

```
D4 fl=1 add=2 t+add luaentities=1 stepped=0
D4 fl=1 add=2 t+3   luaentities=1 stepped=1     ← 存活并 step
D4 fl=1 add=2 t+9   luaentities=1 stepped=1

D4 fl=2 add=3 t+add luaentities=1 stepped=0
D4 fl=2 add=3 t+4   luaentities=0 stepped=0     ← 1 秒后全部被清理
D4 fl=2 add=3 t+9   luaentities=0 stepped=0

D4 fl=1 add=5 t+6   luaentities=1 stepped=1     ← 存活
D4 fl=3 add=5 t+6   luaentities=1 stepped=1     ← 存活
```

数量无关：N = 1 / 2 / 10 / 25 / 100，也无论集中在一个区块还是铺开，只要时序落在竞态窗口里都会被清掉：

```
N=1   one_block D3 t+3-spawn luaentities=1   D3 t+4 luaentities=0
N=100 grid      D3 t+3-spawn luaentities=100 D3 t+4 luaentities=0
```

### 2.3 正确做法（已验证）

`forceload_block` 之后用 `core.emerge_area(..., callback)`，在 `calls_remaining == 0` 时再 `add_entity`：

```
15:01:10  BENCH verify count=100  mode=idle alive=100
15:01:32  BENCH verify count=1000 mode=idle alive=1000
15:01:34  BENCH sample count=1000 mode=idle entities=1000 stepped=1000 steps_per_sec=11.11
```

修复后 100 / 1000 / 2000+ 全部 `alive` 等于目标数量，且 `stepped` 与 `entities` 相等（每个实体每步都被 step）。

## 3. 版本边界与外部对照（后续外部核查补充，必须与上面的数字一起读）

本机 apt 提供的引擎是 **5.10.0**；而 Luanti 在 **2025-04-08 合并了 k-d 树空间索引**（上游 PR #14631），它把 `getObjectsInsideRadius` 这类范围查询显著加速——作者自测（未披露硬件）在 200/1450/10000 对象下由 1.11/10.08/174.8 µs 降到 0.298/0.930/2.54 µs。**5.10.0 不含该索引**，因此第 1.2 节“perceive 崩塌”里包含了一个已被上游修掉的实现代价，不能直接等同于“Luanti 不能做万级邻域感知”。做容量结论前应换到 5.16+ 的引擎重测。

同一来源还给出两条与本文件相关的官方行为：

- `max_objects_per_block` 在源码中被强制下限 `max(256, 设置值)`（`src/mapblock.cpp`）；区块激活时若静态对象数超限，引擎会打印 `suspiciously large amount of objects detected ... removing all of them` 并**清空该区块全部对象**——这是除 emerge 竞态之外的第二种静默清空机制。
- 官方 Lua 优化文档明确：Lua 是单线程且阻塞，“花在 Lua 里的每一秒，服务线程、连接线程和可能的 emerge 线程都完全停住”；`on_step` 每个 server step 都会执行。这与本文件“崩塌来自每实体计算量”的结论一致。
- 社区生产环境实测（GitHub issue #14613 评论，Your Land 服务器，20–50 人、约 6000 实体，未披露硬件）：活跃对象数增长时服务端步频从约 20.8 降到约 7.5；该服 profiling 显示约 40% 服务线程时间花在遍历实体列表。**这是有玩家、有碰撞、有真实地图的负载，比本文件的合成场景更接近现实，应作为下界参考。**
- 官方没有“能承载多少实体”的容量指南，也没有受控的每实体 tick 基准；可自建的官方工具是 `--run-benchmarks`、`/profiler`、F5 profiler 与 Prometheus 指标。

## 4. 结论

1. **无玩家时实体不会被 step，除非区块被 forceload**；而仅仅 forceload 仍然不够，必须等区块 emerge 完成后再放入实体，否则实体在活跃区块管理周期（`active_block_mgmt_interval = 2.0`）中被静默删除。`add_entity` 会返回有效对象，不留错误——这是最危险的一类失败。
2. **2 万实体、每步 O(1) 工作，仍然实时**（11.02–11.04 step/s），峰值 RSS 167 MiB。内存和实体数量都不是瓶颈。
3. **崩塌来自每实体的计算量，而不是实体数**：朴素的 O(N²) 邻域感知在 1000→5000 之间跌破实时（4.4 step/s），10000 时降到 0.92 step/s（每步约 1.09 秒）。
4. 因此千级以上 agent 的关键设计是**感知的空间分区／LOD**，而不是堆硬件。这与研究文档的判断一致，现在有了本项目自己的数字。

## 5. 边界

- 被测实体是合成实体：`idle`（什么都不做）、`move`（每步 O(1) 位移）、`perceive`（每步一次 8 格半径查询）。**没有接入 LLM、没有网络 IO、没有真实 agent 决策**，因此本文件只证明 tick 与内存容量，不证明 agent 行为或 LLM 成本。
- `perceive` 是 O(N²) 的压力代理，不是推荐设计。
- 单一配置、单次运行、本机软件环境；没有多核调优、没有长时间稳定性测试、没有客户端连接，也没有验证有玩家在场时的表现。
- 原始运行脚本与实体基准代码见同目录 `init.lua`、`run.sh`。
