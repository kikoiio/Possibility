## 1. 本轮需求变化

分享中的用户表述逐步明确了三个目标：

- 世界模型在本项目中承担**环境 Simulator** 的职责。角色的意图、认知与自主行为由角色 LLM Agent 负责，Simulator 推演环境自身的演化及角色行动的实际后果。
- 环境需要有更丰富的真实效应，能出现跨系统的影响，而不局限于开发者穷举的简单规则。文本与结构化数据是优先探索的表示路线，LLM 是初始 Simulator 的候选实现。
- 基于 LLM 的 Simulator 需要 Verifier；接下来要解决的是世界与变化如何表示、验证器如何工作，以及模型应收到哪些状态、约束与依据。

因此，原需求中的“纯 LLM 驱动事件、不预设固定行为规则”需要细化：**角色自主性保留；环境推演增加独立职责与验证边界。** 确定性的状态校验与世界约束属于这条路线的一部分，不能因旧表述而排除。

分享中助手进一步提出了因果图、分层验证、规律积累及专用模型训练。这些是研究建议，不能据此认定用户已选择具体架构或要求第一版全部实现。“LLM 一定最便宜”也未经过本项目的预算与质量对照实验。

## 2. 各部分负责什么

以下是待验证的职责划分，不要求每个职责都是独立模型、进程或一次 API 调用。

| 部分 | 职责 | 输出的地位 |
| --- | --- | --- |
| 角色 LLM Agent | 基于自己的观察、记忆与目标，决定想说什么、尝试做什么 | 行动意图；尝试不等于成功 |
| 环境 Simulator | 结合当前事实、行动和时间，推演环境变化与行动后果 | 候选状态变化；尚未发生 |
| Verifier | 检查候选变化的结构、前提、约束与依据，给出诊断 | 接受、拒绝或不确定；接受仍须经过提交检查 |
| 状态引擎 | 管理版本与时间，原子提交通过检查的变化，保留历史 | 已提交的事实与事件 |
| 观察与记忆 | 从已发生事件形成各角色能感知的信息与主观经验 | 角色所知，允许误解与偏见 |
| 渲染与叙述 | 呈现已提交的状态和事件 | 事实的视图，不是第二个事实源 |

例如，暴雨可能改变道路通行能力与粮食运输；居民是否囤货、互助或迁移，由角色根据所知决定。Simulator 不能为了制造戏剧冲突直接指定所有人的选择。环境也应能在无人关注时演化。

这里的“世界模型”指环境动力学的表示与推演能力。`WorldState` 是当前事实容器，3D 场景是其视觉投影；两者都不等于已经实现了环境动力学。

## 3. 先研究可验证的表示

分享中提出的四个维度可作为最小表示的研究起点：

| 维度 | 需要回答的问题 |
| --- | --- |
| State（状态） | 有哪些实体、属性、关系、空间与资源？数量的单位、观测时间和未知值如何表达？ |
| Dynamics（变化） | 哪个行动或环境过程影响了什么？前置条件、作用范围、延迟和依赖是什么？ |
| Constraints（约束） | 当前世界采用什么规律与例外？哪些条件必须由程序检查？ |
| Evidence（依据） | 哪些已提交事实、历史事件或已采用机制支持变化？哪些只是模型假设？ |

候选变化协议可先讨论以下信息，**字段与存储形状未定，不是 contract 草案**：

- 所属世界线、基准 revision、推演时间窗与规律版本。
- 输入行动的 ID、执行者、目标与尝试内容；自然环境过程也可独立成为原因。
- 读取的状态、前置条件、涉及实体与字段，以及机制摘要和可引用的依据 ID。
- 直接后果、延迟后果与它们之间的依赖；每项变化关联拟提交的 ops。
- 不确定性、缺失条件和候选次生效应；这些信息不能直接转成事实。模型自报的置信度不能当作已校准概率。

例如，“暴雨造成短缺”必须能落到道路、运输量和库存等具体状态上。若只写进事件文本、没有相应状态变化，后续角色仍拿到旧库存，环境模拟就没有成立。示例数值只用于测试协议，不代表科学预测。

世界中的魔法、特殊物理规律或用户设定的例外应能明确表达。哪些规则可修改、如何版本化和随“如果…”分岔，仍待设计。

## 4. Verifier 的能力边界

以下分层来自分享中的助手建议，尚需原型验证：

| 层 | 可用依据 | 能验证什么 |
| --- | --- | --- |
| 结构与硬约束 | Schema、代码、当前世界已声明的约束 | 引用、字段、单位、范围、资源账目、时间与依赖是否一致 |
| 因果一致性 | 已提交状态、历史、机制、必要时 LLM 审查 | 前提是否成立，有无反例、跳步或凭空补出的事实 |
| 幅度与时间 | 可执行领域模型、参考数据或明确设定的世界规律 | 效应的量级、速率、延迟是否有支持 |

资源守恒等规则须说明适用域和例外；不能把所有幻想世界硬套为现实物理。另一个 LLM 同意某个结果，只能构成语义审查，不能证明现实准确性。在缺乏外部真值的虚构世界中，应明确区分“符合已声明的世界规律”和“符合现实”。

建议的失败语义：硬约束失败则拒绝；依据不足则标记不确定、补信息或在预算内返修。不把不确定静默当作通过，也不无限互相重试。诊断需要定位候选变化、失败条件和所缺信息。

未出现过的机制不能仅因规则库中没有就被否定；同样，也不能仅凭一次生成与一次赞同就成为永久规律。候选机制与已采用机制如何区分、如何验证后升级，作为后续研究项。

## 5. Prompt 要依赖明确输入

Prompt 的研究重点是输入和职责边界，而不只是换一段系统提示词：

- **角色输入**：角色自己的观察、可见记忆、目标和可尝试的行动。隐藏事实不能因为 Simulator 需要全局状态就顺带交给角色。
- **Simulator 输入**：基准状态、已采用的世界规律、相关历史、行动尝试与时间窗。输出候选变化、机制摘要、依据引用及未知项，不直接写事实或替角色选择意图。
- **Verifier 输入**：同一基准及规律版本、原始依据、候选变化和确定性检查结果。检查依据是否真的存在，不能只读 Simulator 的自我解释。

角色的谎言、偏见与事后讲法不按客观事实真假直接驳回；它们与环境事实变化属于不同语义，沿用[记忆设计](DESIGN-memory.md)的 L0/L1/L2 区分。Verifier 也不负责让剧情更好看。

角色与 Simulator 是否分别调用、能否批量生成、何时触发额外审查，均待成本实验。新增调用必须计入现有跨线预算和审计，不能默认每个节拍、每个角色都调用一整套模型。

## 6. 当前代码与目标之间的差距

2026-10-25 只读核对，当前路径仍是单个 beat 生成叙事事件与 ops：

| 现有证据 | 已有能力 | 尚缺能力 |
| --- | --- | --- |
| [`llm/assemble.ts`](../../packages/engine/src/llm/assemble.ts) 的 `assembleBeatMessages` | 世界、近期事件与角色记忆组装为叙事 prompt | 角色决策与环境推演的独立输入、输出边界 |
| [`domain/index.ts`](../../packages/engine/src/domain/index.ts) 的 `validateOps` / `validateWorld` / `validatePlan` | 路径、实体引用、部分时间及记忆字段检查，演算候选 ops | 显式因果依据、领域约束、资源账目、效应幅度与延迟验证 |
| [`runtime/index.ts`](../../packages/engine/src/runtime/index.ts) 的 `generateBeat` / `commitDueEvents` | 接受计划、到期提交 revision 与记忆 | 独立的 Simulator / Verifier 流程与验证记录 |

已有结构校验可以作为验证底座，但不能称为完成了 World Verifier。当前全量世界输入也需要在拆分角色调用时复核；按 owner 筛记忆并不自动隔离 `WorldState` 中的隐藏事实。

### 与现有边界衔接时必须讨论的事项

- 所有被接受的变化仍经 ops、revision 与事务提交；环境模拟不能另开一条直接写世界的路径。对话引发的行动后果也要覆盖，不能只验证 beat。
- 长计划的延迟结果依赖什么前提？中间发生对话、干预或其他事件后，如何失效、重验和重算？接受计划不等于未来结果已发生。
- “如果…”改变环境条件后，待执行的效应、机制版本与验证依据如何隔离？不能把父线基准下的结论直接沿用到子线。
- 重启与历史读取沿用已保存的结果；不通过重新调用模型伪装为同一历史。模型随机性与用户干预造成的差异仍需分开评估。
- 如需修改跨模块 DTO、Plan 或调用类型，按 [ARCHITECTURE.md](ARCHITECTURE.md) 的契约变更协议统一更新消费者，本文不预先新增接口。

## 7. 最小验证方向与开放问题

建议先选一个有明确检查依据的小场景，对比当前 beat 与候选 Simulator + Verifier；场景、指标阈值和实现优先级尚未裁定。

候选场景：持续降雨影响一条道路、两个地点的运输与库存，角色再决定是否绕路或修路。环境状态可以在无人行动时变化；同一条件下有排水设施与无排水设施应有可解释的差异。

验证至少覆盖：

1. **实际状态**：影响落实到可查询字段；无关实体保持一致，未观察到变化的角色不凭空知情。
2. **约束与延迟**：非法资源变化被拒绝；延迟效应按时间及前提执行，前提改变后不会照旧提交。
3. **跨步与跨线**：多步传播不漏依赖、不重复扣资源；暂停、重启和分岔后无跨线污染。
4. **拒绝与不确定**：植入错误、缺失依据和未知机制，检查误放行与误拒绝，保留诊断。
5. **收益与成本**：固定初态和外部输入，对照硬约束失败、因果遗漏、多轮漂移、调用量与延迟；真实感另由用户把玩判断。

下一轮需要收敛：

- 第一批要模拟哪些环境效应、在哪个尺度上算“真实”？采用哪些世界规律与例外？
- 什么是支持这些效应的最小状态与变化协议？何时需要可执行机制，而非仅文字说明？
- 验证依据不足时如何处理？哪些检查必须确定性执行，哪些值得增加模型调用？
- 角色行动、自然演化、延迟效应与现有 beat 如何调度？怎样保住角色可见域和总预算？

| 一手资料 | 与本项目相关的部分 | 适用边界 |
| --- | --- | --- |
| [Concordia 官方仓库](https://github.com/google-deepmind/concordia) | Agent 提出行动，Game Master 产生观察并裁定后果，engine 组织执行 | 可参考职责与循环，不代表已解决开放环境的真实性验证 |

## 9. 后续讨论记录与状态

以下按本次会话中的议题先后记录；同日条目不虚构精确时间。设计细节仍以上方导航中的对应文档为准。

### WM-D01：补充研究与公开实现

- **用户要求**：继续搜索分享中提到的研究，并补搜优秀研究与公开实现，用于深入讨论。
- **资料核对**：分享项目之外，补充 WorldAgent、WorldLLM、EMPIRIC、AWM、DiscoveryWorld，以及 Code World Model、PWM、CoDeR 等。来源、阅读深度、未复现范围和其余线索保存在[调研文档](WORLD-MODEL-RESEARCH.md)。
- **形成的研究判断**：学习一个已有环境、构造一个新环境、评估环境是否正确是不同任务。许多方法有可执行环境、数据或案例作为验证依据；Wispiva 需要自己说明验证依据从哪里来。
- **限制与修正**：NeSyS 的规则评分不等于通用真实动力学；AWM 的任务完成 verifier 不等于环境效应 verifier；有项目页或公开仓库不等于完整实现已发布。这些都是调研判断，不是已经通过本项目实验的结论。

### WM-D02：逐轮生成与机制复用

- **助手建议，未定**：比较每轮由 LLM 提出状态变化、由 LLM 构造并复用机制，以及已采用机制与开放推演结合的路线。
- **支持依据**：WorldCoder 提供从经验修订程序的研究，WorldLLM 提供文字假设与主动探索，EMPIRIC 提供在基础模拟器上补缺失机制的研究；各自的验证锚点和范围不同。
- **仍开放**：第一次出现的机制如何裁定、采用后怎样修订/撤回、是否值得执行代码，以及输入表示与机制知识分别贡献了什么。
- **状态**：用户尚未选择运行路线，不能把“机制复用”或“LLM 生成代码”写成已确认需求。

### WM-D03：RSI 的含义与适用范围

- **用户提问**：“RSI?”。本轮按 Recursive Self-Improvement（递归自我改进）解释，未据此推断用户要求实现 RSI。
- **讨论要点**：更好的世界模型若帮助选择更有效的实验、发现反例并进一步改善建模，可形成围绕世界模型的改进闭环。仅积累规则与“改进后续学习能力”需要区分；底层 LLM 可以保持固定。
- **补查资料**：[Memento 3](https://arxiv.org/abs/2610.11794)以外部规则书、代码世界模型和观察转移重放研究这类路线；本轮只核对摘要。原理与阅读边界补入[调研文档 §3](WORLD-MODEL-RESEARCH.md#3-补搜中值得深入的工作)。
- **状态**：后续研究方向，未纳入当前交付。自生成轨迹的内部一致性仍不能独立证明现实准确性。

### WM-D04：世界表示是首要难题

- **用户明确指出**：世界如何表示才是第一个大难题，讨论应回到这个问题。
- **优先级调整**：先明确表示，再讨论 Simulator、Verifier 和后续自我改进。这是当前推进顺序。
- **助手提出的分析**：文本可读写不等于语义已解决；开放 JSON 仍需定义实体、关系、属性含义/单位、持续过程、未知/估计/假设和角色所知。持续过程的状态与未来预测分开；扩展表示时保留此前的未知，不能补写历史。
- **候选与例子**：同雨量、不同排水的后果应可区分；干/湿木桌遇火作为跨领域检查。A“属性快照与文字过程”、B“语义组件与显式过程”、C“可执行机制优先”是待比较候选，不是用户已选择的结构。
- **状态**：已进入[世界表示设计草案](DESIGN-world-representation.md)，具体概念划分、粒度、未知处理和版本规则仍待收敛。

### WM-D05：当前架构支持范围

- **用户询问**：如何在项目中实践，当前架构是否支持。
