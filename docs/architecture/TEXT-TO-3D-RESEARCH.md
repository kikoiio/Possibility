# 文本生成可编辑 3D 世界的路线调研

日期：2026-10-24。
状态：技术调研与候选方案，尚未通过 Wispiva 实测，不是冻结的实施契约。

## 要解决的问题

用户用文本创建自己想要的世界。世界必须好看，能容纳角色活动，能继续编辑，并能在任意版本分岔。已确认只提供 3D，不再开发独立 2D 模式。

生成能力取决于用户接入的模型。系统负责提供结构化表达、语义工具、空间反馈和修改接口，尽量降低模型的生成难度。成品资产库和固定建筑模板不能成为创作的唯一入口。

本轮阅读论文、作者项目和服务官方文档，没有调用收费生成接口、下载模型权重或运行 GPU 实验。下文区分外部已报告能力与我们据此提出的设计建议。

## 先区分世界表示与生成方式

体素、三角网格和 Gaussian splats 是内容的表示方式。LLM 写程序、调用建模工具、专门模型生成网格是生成方式。它们可以组合，不应当作为互斥的产品路线。

体素不要求使用固定建筑模板。模型可以通过区域填充、复制、旋转、对称和自定义组合构造新建筑。模板数量不能说明体素的表达上限。

程序化建模也不天然局限于低多边形或平涂美术。Infinigen Indoors 展示了程序化资产、材质和约束布局可以形成写实场景，但开发生成器本身需要投入。它没有证明我们可以低成本覆盖任意题材。[论文](https://arxiv.org/abs/2406.11824)

## 已有路线及其对 Wispiva 的意义

| 路线 | 模型实际生成什么 | 证据 | 对 Wispiva 的判断 |
| --- | --- | --- | --- |
| 文本到体素蓝图 | 建筑分区、材质、坐标区域或生成蓝图的程序 | [T2BM](https://arxiv.org/abs/2406.08751)、[APT](https://arxiv.org/abs/2411.17255) | 值得保留为主要候选。可编辑性强，能靠通用操作组合出新形状。要测输出长度、细节与局部修改质量。 |
| 文本到建模程序 | Blender Python、几何操作、材质节点 | [SceneCraft](https://arxiv.org/abs/2403.01248)、[LL3M](https://github.com/threedle/ll3m) | 可突破有限成品资产库。程序可保留参数，但代码能运行不等于好看，必须有反馈和修订。 |
| 场景规划与资产布置 | 场景图、物件关系、尺寸与位置约束 | [Holodeck](https://arxiv.org/abs/2312.09067)、[SceneSmith](https://scenesmith.github.io/) | 适合做总体组织。单靠检索资产仍受库存限制，需要连接其他生成方式。 |
| 文本或图像到物件网格 | 几何、纹理，有时提供重拓扑与动画工具 | [Meshy API](https://docs.meshy.ai/en/api/text-to-3d)、[TRELLIS.2](https://github.com/microsoft/TRELLIS.2) | 可按需补充特殊物件。生成后仍需检查尺寸、方向、部件和运行性能。 |
| 按语义部件生成物件 | 一个物件及指定名称的独立部件 | [CubePart](https://about.roblox.com/newsroom/2026/05/cubepart-roblox-open-vocabulary-part-controllable-3d-generator) | 很适合参考交互资产接口。部件语义不应限于预定义的建筑种类。尚需验证具体模型与接入成本。 |
| 文本或图像到完整空间 | 网格、Gaussian splats 等可浏览空间 | [World Labs World API](https://www.worldlabs.ai/blog/announcing-the-world-api)、[HY-World 2.0](https://github.com/Tencent-Hunyuan/HY-World-2.0) | 应纳入候选。能浏览或导出，不自动证明支持我们需要的门窗状态、物件身份、角色寻路和局部版本编辑。 |

T2BM 用 JSON 中间表示描述墙、屋顶和功能部件，避免逐块自然语言描述。APT 则用程序生成 Minecraft 蓝图，并支持根据多视角截图修订。两者支持分层表达这个方向，其实验范围不足以证明可以自动建造任意高质量世界。[T2BM 方法](https://arxiv.org/html/2406.08751v1)、[APT 方法](https://arxiv.org/html/2411.17255v2)

SceneCraft 使用场景图、代码与视觉反馈。LL3M 使用 Blender 建模程序并支持后续指令编辑。LL3M 仓库同时说明论文所用服务已经停止，因而可借鉴方法，不能把演示服务当成当前可用依赖。[SceneCraft](https://arxiv.org/abs/2403.01248)、[LL3M 仓库](https://github.com/threedle/ll3m)

## 模型无关不等于结果与模型能力无关

这里的模型无关应定义为：创作模型、视觉复核模型和几何构造后端都可替换；质量流程不绑定某家模型的私有输出格式。它不意味着弱模型与强模型得到同样好的世界。MineAnyBuild 对 13 个多模态 agent 的测试显示，不同模型的可执行蓝图成功率差异很大；即使强模型也常采用方正、保守的设计。论文报告的 GPT-4o 总分为 41.02/100，特定空间旋转测试中表现最好的受测模型也只有 26.7% 正确率。这些是论文任务与版本下的结果，不是当前所有模型的永久排名，但足以说明不能把“模型会写建筑代码”当成空间问题已经解决。[NeurIPS 论文](https://arxiv.org/html/2505.20148)

我们能负责的是降低表达难度、让错误可观测、让修改不必推倒重来。建议把质量保证做成与具体模型无关的流水线：

1. **语义分解**：先形成区域、物件、部件、材质和连接关系，再生成局部几何，避免一次输出整个世界。
2. **分层构造**：提供区域、挤出、旋转、曲线、阵列、开洞等通用操作；允许模型定义新部件和新配方，而不是只能选择预设建筑。
3. **确定性空间执行**：模型声明局部坐标、锚点、接口与约束，程序完成吸附、对齐、变换求解、尺寸检查和碰撞查询。
4. **结构验收**：检查生成操作是否有效、部件是否连接、开口是否存在、入口能否到达、活动空间是否足够；错误返回稳定 ID 和结构化诊断。
5. **可选视觉验收**：把多视角图、部件着色图、原始意图和结构诊断交给独立复核模型，每次只修订已定位的问题。视觉评价不能替代空间检查，也不能作为唯一审美裁判。
6. **保留与回退**：保存每次已接受的局部版本。失败可以返回上一个版本，未改动部件不得被重新随机生成；预算耗尽时报告未完成项。

Procedura 是这条路线目前很直接的参考。它让模型逐部件编写参数化 CSG，以有类型的 mate 描述装配关系，由程序求解放置；编译、接口注册、穿插和连通性检查之后，再由独立视觉 critic 定位并触发局部修订。它输出的不是一团无语义三角形，而是仍可编辑的部件程序。[论文](https://arxiv.org/html/2608.26238v1)、[官方仓库](https://github.com/SpatiaOS/Procedura)

但证据边界必须写清楚：Procedura 的主要任务是机械物件与装配，不是任意世界的美术生成；作者也指出被遮挡的内部和精细接触可能逃过所有渲染视角，需要剖面、深度或网格查询。其论文消融支持规划、3D 反馈和修订有贡献，同时部分模型上的美学提升并不显著，单次强模型也已经取得很高基准分。因此应借鉴其闭环，不应宣称这套流程必然超过直接提示强模型。

ShapeAssembly 更早证明了以 cuboid、attach、squeeze、reflect 等操作组成参数化形状程序的价值；同一程序可表达一族形状并支持局部编辑。它是特定 DSL 与学习模型的研究，不是现成的通用世界生成器。[论文](https://arxiv.org/abs/2009.08026)、[代码](https://github.com/rkjones4/ShapeAssembly)

## 通用几何与体素到底差在哪里

| 维度 | 通用参数化几何 | 体素 / 方块构造 |
| --- | --- | --- |
| 模型的主要工作 | 设计部件、形状操作、接口和装配关系 | 设计区域、层、图案、材料和重复结构 |
| 几何表达 | 曲面、斜面、任意尺度细节、精确实体 | 栅格采样；细体素或台阶、斜台阶等附加形状可减轻阶梯感 |
| 最容易出错的地方 | 布尔拓扑、穿插、悬空、连接与比例 | 输出过长、逐格空间错误、形体保守、细节重复 |
| 局部修改 | 修改参数或部件，重编译受影响节点 | 修改区域或图案，重建受影响区块 |
| 与角色活动的连接 | 需要额外构造碰撞、入口和导航表面 | 可直接从占用格派生候选碰撞与导航，但门、台阶和非立方体仍需语义 |
| 美术上限 | 不受体素轮廓限制，但造型、材质与光照不会自动变好 | 已有统一语言，轮廓、材料层次和光照仍能产生很高上限 |
| 浏览器工程 | 需要实体内核或可靠的网格操作、拓扑与面数治理 | 数据简单、增量局部；需要区块网格化、剔除、透明与材质处理 |

通用几何并不是“让 LLM 自由写三角形”。更合适的是让它写受约束的部件配方，由可信几何工具执行。Manifold 提供面向实体网格的布尔与变换操作、manifold 输出保证以及 JS/WASM 接口，是默认 JS 环境值得实测的候选；这个保证不等于生成结果好看，也不等于所有导入网格都自动可修。[官方文档](https://manifoldcad.org/docs/jsuser/)、[仓库](https://github.com/elalish/manifold)

因此，默认实现可以先共享以下文档与产物接口，而不是复制两套编辑器：

```text
SceneDocument
  region / object / part / attachment / material / interaction
       |
       +-- voxel recipe --> chunk cells --> render mesh
       |
       +-- solid recipe --> editable mesh --> render mesh
       |
       +-- optional external asset --> validated mesh
```

`SceneDocument` 保存身份、关系与交互，不要求所有后端有相同的底层操作。编辑器操作区域、物件和部件；只有对应工具才暴露体素笔刷或实体参数。渲染器消费统一的带稳定 ID 的网格与材质产物。这保留了后端替换能力，也避免把“未来可能换后端”变成永久维护两套完整产品。

## Minecraft 为什么成功，AI 为什么容易接入

Minecraft 的成功不能只归因于体素存储或方块便宜：

- **有限操作具有组合性**：放置、删除、复制、旋转与材料组合可以构造没有预制模板的作品；规则统一使结果可预测，局部试错成本低。
- **表示、交互和视觉一致**：玩家看到的就是可编辑空间，不需要在“模型描述”和“真正场景”之间猜测映射。这个功能身份也是 T2BM 特别强调门、窗和室内部件的原因。
- **风格统一而非细节贫乏**：材质色板、纹理、重复图案、建筑比例、轮廓、进退层次和细部尺度共同决定观感。台阶、楼梯、墙、栅栏等并不只是一个完整立方体，不能把所有方块都简化成同一 box。
- **展示品质包含渲染**：光照、阴影、反射、雾与镜头会显著改变同一建筑的效果。Minecraft 官方 Vibrant Visuals 就在保留方块语言的同时加入体积光、阴影、反射和材质响应；这说明“采用体素”远不是美术工作的终点。[官方介绍](https://www.minecraft.net/en-us/article/minecraft-vibrant-visuals)
- **工具与社区放大上限**：蓝图、批量编辑、结构复用和玩家作品提供了创作经验。AI 可以直接生成蓝图或构造代码，无需像真实玩家一样逐块移动和放置。

AI 接入后容易得到可展示结果，还因为输出空间明确、材料名称语义丰富、结果可以立即在成熟游戏里渲染和复查。APT 先生成布局说明，再写 Python 蓝图，最后通过 Mineflayer 执行并可选视觉反思；T2BM 用带部件与坐标的 JSON 中间层和修复器；CraftUtopia 把图样分区给不同 worker，并沉淀成功操作序列。这些都是“模型提出计划，程序可靠执行”，不是模型直接产生像素画面。[APT](https://arxiv.org/html/2411.17255v2)、[T2BM](https://arxiv.org/html/2406.08751v1)、[CraftUtopia](https://github.com/RGB-0000FF/CraftUtopia)

不能把社交媒体上的最佳作品当作普遍能力。Creative Agents 的最佳受测组合使用扩散想象与 GPT-4V，但论文仍报告简单建筑、循环生成的原始墙体、寻路破坏和体素重建问题。MineAnyBuild 也显示“有创意描述”与“可执行、空间正确的建筑”之间存在明显缺口。优秀案例证明可能性，基准与失败案例才决定默认流程该怎样兜底。[Creative Agents](https://arxiv.org/html/2312.02519)、[MineAnyBuild](https://arxiv.org/html/2505.20148)

## 体素实现与性能不是每格一个 Mesh

Java Edition 的持久化区块格式以 16×16×16 section 保存调色板和打包后的方块状态索引；空或单一状态区域可以紧凑表示。这个结构适合局部读写，但磁盘格式不是渲染格式。[格式文档](https://minecraft.wiki/w/Chunk_format)

一个可扩展体素渲染器至少需要：

1. 以区块保存单元数据，只给可见表面生成几何；读取相邻区块边界，避免内部面和接缝重复。
2. 在 worker 中构造并缓存区块网格。局部修改只标脏所在区块及必要邻居，异步结果按版本提交，禁止旧任务覆盖新编辑。
3. 按材质与透明类别组织批次，使用纹理图集或数组，复用顶点、索引与实例数据；不能为每个 voxel 建一个 Three.js `Mesh`。
4. 进行视锥剔除，并评估区块可见图或 GPU 遮挡剔除。远景使用距离调度、加载预算或 LOD，透明体素单独处理排序。
5. 将平滑光照、AO、材质尺度和纹理重复纳入网格与着色设计。Greedy meshing 只适合合并光照、材质、透明和 AOI 等顶点属性相容的共面区域，不是无条件减少全部面。

Sodium 是高质量实现参考，而不是一段可以照抄到浏览器的算法。其当前源码包含按 section 的网格构建任务、按优先级调度与上传预算、邻区数据、区块可见性遍历、共享 quad index buffer 和区域绘制批处理。它说明性能来自整个数据与调度系统，而不只是 greedy meshing。[网格任务](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/compile/tasks/ChunkBuilderMeshingTask.java)、[区块调度](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/RenderSectionManager.java)、[遮挡遍历](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/occlusion/OcclusionCuller.java)

Wispiva 如果走体素，也不表示视觉必须复刻 Minecraft。体素尺寸、非整格部件、材质、角色、植被、光照和镜头都仍需自己的美术方向。更不能直接复制 Minecraft 品牌与资产。[官方使用准则](https://www.minecraft.net/en-us/usage-guidelines)

## 对当前技术判断的修正

“通用几何自由度更高，所以应该直接取代体素”和“体素容易，所以先做 Minecraft 就行”都过于简单。真正的差异是：**体素把大量造型问题转化为统一栅格上的组合问题；通用几何保留更多形状自由，同时把拓扑、装配和视觉质量的更多责任交给我们。**

当前最值得验证的是同一个高层创作闭环下的两种构造后端。若通用几何在相同模型、预算与修订次数下仍只能产出拼装感强的 primitive，而体素在目标题材上明显更好看、更易修改，就应选择体素作为主后端；反之，若曲线、精细部件和非栅格造型是用户实际需求的瓶颈，则应优先通用几何。选择应由成品与编辑实验驱动，不由对 Minecraft 上限的低估驱动。

## 多模态能帮助创建和检查世界

多模态模型可以读取用户参考图，也可以检查我们自己渲染的场景。后者可发现桥接错岸、入口被遮住、建筑比例失衡等问题。Scenethesis 将语言规划与视觉引导、空间优化和复核结合，是一条相关路线。[作者项目](https://research.nvidia.com/labs/cosmos-lab/scenethesis/)

视觉反馈需要配合结构化数据。仅看截图可能分不清遮挡、空洞和真实可通行空间。建议给复核模型同时提供多视角图、物件 ID 标记、尺寸、入口与校验结果，由模型返回引用物件 ID 的修改提案。

日常角色推演可以继续读取符号化世界信息。创世或大幅编辑时是否启用视觉反馈，由模型能力与预算决定。无需每个模拟节拍重新生成图像或整座世界。

CubePart 的关键启发是让调用方声明所需部件，例如车身、车轮与车灯，再生成对应的独立网格。官方也指出其刚体部件仍可能重叠，空间区分和有机角色蒙皮仍有局限。部件可分离也不等于行为已经正确。[官方说明](https://about.roblox.com/newsroom/2026/05/cubepart-roblox-open-vocabulary-part-controllable-3d-generator)

## 成本和可调用性必须单独验证

SceneSmith 表 18 报告，179 个房间的平均生成成本为 13.98 美元，平均耗时为 3 小时 26 分。时间是在 8 张 L40S 上同时生成 25 个场景的吞吐评测设置中测得，不能视为优化后的单场景延迟。这支持借鉴流程，不支持直接照搬整套系统作为即时创世服务。[论文附录 O.5](https://arxiv.org/html/2602.09153v2#A15.SS5)

TRELLIS.2 官方发布的是图像到 3D 资产管线。仓库要求至少 24GB NVIDIA 显存，项目页秒级耗时在 H100 上测得。不能把它理解为普通本机可以达到的速度，也不能把它当作直接接受文本的接口。[官方仓库](https://github.com/microsoft/TRELLIS.2)、[项目页](https://microsoft.github.io/TRELLIS.2/)

Meshy 已公开文本生成 3D 的异步 API，文档包含 GLB 输出、面数与拓扑控制。已有 API 不等于生成的对象满足室内、可交互和风格统一要求，这些需要在我们的场景里验收。[API 文档](https://docs.meshy.ai/en/api/text-to-3d)

World Labs 已公开 World API。HY-World 2.0 官方仓库列出了生成和重建能力及分阶段开源记录。此前认为没有可调用的空间生成模型，或者它们只适用于真实场景，都不准确。具体编辑粒度、许可、费用和模型版本仍要逐项确认。[World API](https://www.worldlabs.ai/blog/announcing-the-world-api)、[HY-World 仓库](https://github.com/Tencent-Hunyuan/HY-World-2.0)

## 建议先验证的系统结构

以下是根据调研提出的 Wispiva 设计，不是上述项目已经替我们验证的结论。

### 默认运行环境约束

项目默认使用本机 Node 24 服务与浏览器，未来支持自托管常驻服务。默认安装不应要求 Blender、CUDA、Python 建模工具链或本地 3D 模型权重。论文使用某项工具，不表示该工具适合作为产品的必需依赖。

2026-10-24 只读检查显示，当前开发机为 i5-13500HX，系统可见 RAM 约 14GiB，RTX 4060 Laptop 显存约 8GiB。检查时 MemAvailable 约 7.4GiB、memory PSI 的近期平均值为零。这些是单次开发环境观测，不是所有用户的最低配置，也不代表大场景已经通过性能验收。

| 部分 | 默认执行位置 | 对运行环境的要求 |
| --- | --- | --- |
| 创作模型、角色推演模型 | 用户配置的模型服务 | 通过 API 调用，不默认在本机加载模型权重。自部署模型可作为另行配置的端点。 |
| 世界事实、历史、生成任务状态 | Node 服务与 SQLite | 不依赖 GPU，也不要求观看页面一直打开。 |
| 场景配方处理与几何构造 | 受预算限制的 CPU 任务 | 首先验证可在 JS 环境执行的构造操作。浏览器任务移出主线程，服务端任务避免阻塞时间调度。 |
| 实时 3D 渲染、相机、视觉动画 | 用户浏览器 | 使用客户端 GPU，按设备、分辨率和视口数量测量并设置质量档。 |
| 视觉复核 | 浏览器提供预览图，调用用户配置的视觉模型 | 作为创作阶段可选能力。普通 headless 云服务器不必为此常驻浏览器与 GPU。 |
| Blender、专门的网格生成或完整空间生成 | 可选生成后端 | 单独部署或调用外部服务，不能成为基本创世和日常运行的必要条件。 |

因此优先验证的两条路线，都应先输出可在 JS 环境处理的配方。一条是体素区域与组合操作，另一条是通用几何与组合操作。Blender 论文提供方法参考，但不能直接替换成默认执行后端。

浏览器关闭后，服务端继续维护角色与世界事实，无需给无人观看的世界线持续渲染画面。分屏对照有额外 GPU 成本，不能因共享资产就认为多视口没有开销。目标设备范围，尤其是否要求手机完整创作体验，仍需确认。

本机优先并不等于模型推理必须离线。产品的生成费用与服务访问权限由用户配置。GitHub Actions 等免费 CI 用于经授权的开发验证，不能充当用户持续创世的免费推理服务。

```text
用户文字，可选参考图
    |
创作模型：规划区域、物件、部件、外观和空间关系
    |
可编辑场景文档与生成配方
    |
生成任务：体素构造 / 程序化建模 / 可选资产模型
    |
结构检查、布局求解、可选多视角复核
    |
用户预览与局部修改
    |
提交世界版本和固定的生成产物引用
    |
3D 渲染与角色推演
```

建议先用体素与通用建模操作做两条对照实验，共享场景文档和布局接口。特殊网格资产作为可选第三条路径。是否以体素为主要表示，在实测后决定。

### 语义帮助必须能向下展开

提供跨题材的结构工具，例如区域填充、挤出、曲线、旋转体、开洞、复制、阵列、变换、材质、分组和可复用定义。有限工具可以组合出没有预设过的物件，但仍受工具能力、模型能力和预算限制。

建筑、桥梁和树木等高级生成器可以降低难度。它们应允许替换部件、修改参数或展开后编辑。不要把全部世界锁进茶馆、塔、民居等封闭枚举。

模型也可以按能力获得更细的工具。强模型可以构造新的配方，弱模型可以调用已经存在的配方。先用相同任务测量，不能假设增加抽象层一定改善所有模型。

若支持模型生成代码，将执行放在受资源限制的独立生成任务中，收取场景数据和网格产物。浏览器的世界运行循环不直接执行未经处理的生成代码。

### 让模型表达关系，程序提供可靠的空间操作

模型可以说桥连接两岸、门位于临街墙面、椅子面向桌子。布局系统处理对齐、吸附、间距和避让，并返回冲突物件与位置。

允许局部坐标和精确数值。坐标系、单位、朝向、锚点、占地、出入口需要明确，不能靠删除数值表达来回避空间问题。

校验失败返回结构化诊断，保留用户意图。不要把未知物件静默替换成普通房子后声称生成成功。美学要求与硬性空间条件分开，部分超现实设定可能有意违反重力或普通建筑规则。

### 世界状态与几何产物之间保留稳定的身份

每个参与故事或交互的物件有稳定 ID。世界文档记录角色位置、空间关系、物件状态和生成配方引用，渲染层用这些 ID 找到网格、体素块组和动画节点。

门可以有开合状态、铰链与通行区域。它可以使用程序几何，也可以使用专门模型生成的部件。物件身份和交互语义不依赖具体网格格式。

保存确认后的产物、内容哈希、配方、生成器版本和参数。相同 seed 不保证跨模型重新生成相同结果。历史回放和 fork 复用已经确认的内容，仅为变化部分创建新产物。

### 生成预算与运行预算分开

创世可以分阶段预览并继续细化。角色活动、镜头移动和普通节拍不触发场景重建。复杂资产只生成受影响部分，并按内容复用。

模型上下文按当前区域或物件查询，不要求每次携带全世界的顶点和纹理。场景文档需要可查询的结构，几何大文件独立保存。

运行端对网格面数、材质、纹理、实例数和显存设置预算，超额时报告或降级。目标帧率必须在指定设备、分辨率与多线视口数量下测量，不能把某个引擎的 mesh 数测试直接换成我们的 draw call 预算。

## 渲染引擎暂不作为生成路线的约束

Three.js 可以继续作为候选，因为旧视觉代码基于它。它不决定内容必须是体素、低多边形或何种美术风格。官方 WebGPURenderer 支持 WebGPU 与 WebGL2 后备路径，但旧着色器能否迁移仍需检查。[官方说明](https://threejs.org/manual/pages/webgpurenderer)

PlayCanvas Engine 可脱离在线编辑器独立使用，此前把选择它等同于必须绑定云工作流不准确。[官方文档](https://developer.playcanvas.com/user-manual/engine/standalone/)

现阶段更需要确定场景文档、建模操作和产物接口。无需为了尚未验证的引擎替换能力实现多套渲染后端。

## 选型实验要测创建、修改和分岔

建议使用同一组文字描述，对比体素构造、通用建模操作和可选网格生成路线。至少覆盖临水茶馆及室内、悬空图书馆、科幻温室和一个陌生复合物件，避免只验证已写好的江南建筑模板。

每条路线保留完整尝试和失败，比较多个用户可接入的模型。用同一预算记录提示词、调用数、耗时和费用，同时评估以下结果：

- 用户是否觉得好看，画面是否符合描述，风格是否统一。
- 外部和内部是否都成立，多视角是否暴露破面或缺失结构。
- 门能否使用，角色能否进入与活动，物件能否被独立选中。
- 修改建筑某层、移动门或替换部件时，能否保留未改动内容。
- fork 后原线是否不变，重开历史是否复用同一份已确认内容。
- 在目标设备上的加载时间、帧时间、内存与显存占用。

本轮只提出实验。后续 GUI 演练和重型生成按本机资源规则优先放云端，调用云端账号或上传代码前另行告知服务、用途和权限并取得许可。

## 尚未定案的内容

主要几何表示、默认美术方向、允许的等待时长、可选资产生成预算、角色外观与动画方案均未定案。现有原型观察不能代替这些验证。

目前最有依据的方向是让模型生成可编辑的结构与配方，系统负责构造、检查和保存。多模态复核与专门的 3D 模型可以参与，体素也仍是有竞争力的候选。

## 第一轮手写构造原型

2026-10-24 增加一次性对照实验 `scratch/geometry-lab`，观察记录见该目录的 `OBSERVATIONS.md`。第一轮为两个手写配方；后续已实现共享 `SceneDocument`、参数驱动双后端、按配方内容增量替换与空间验收，并用改 ID / 旋转 / 平移 / 改尺寸的陌生场景和浏览器文档编辑复验。它仍是有限语义子集，没有调用 LLM，因此没有解决生成路线选型，也不构成美术或完整导航验收。

初始版本 B 的静态统计为：通用几何约 2.16 万三角面、246 个网格/实例批次；体素约 11.51 万面、34 个批次。它说明面数、绘制批次和实际帧时间必须分别测量，不能根据表示方式推断性能。软件 WebGL 截图已检查桌面、手机、室内和局部编辑；真实目标 GPU 性能仍未验证。
