# Wispiva v1 架构竞赛 · Grounding

日期：2026-10-24 · 依据：docs/requirements.md（已确认）+ prototype/（机制已冒烟验证）

## 已确认的产品事实（不可妥协）

1. 单一第一用户（作者本人），本机优先；未来可自托管云端 7×24。
2. 世界线持续运转，真实时间耦合，默认 24×（1 真实小时 = 24 世界小时），可加速可暂停。
3. "如果…"任意时刻可发起：批量修改任意世界状态 → 确认 → 新世界线分岔，原线不变；所有线并行运转。
4. 纯 LLM 驱动事件（无固定规则内核）；prompt 带角色现状/关系/近因；调用节拍与成本由用户配置。
5. 实时画面必须（2D 与 3D 渲染并行提供）；完整历史 log；带 LLM 的世界编辑器。
6. 术语：世界线 / 如果… / 多元宇宙。

## 原型验证结论（事实）

- tick 驱动可行：真实时钟按倍速换算世界时间，跨过 beat 边界触发一次 LLM 推演，事件带 offsetMinutes 落到时间轴。
- fork 采用"深拷贝 + log 引用共享前缀"，内容级 diff 找 first divergence；但原型里是内存态，重启即失。
- mock 引擎证明了移动/状态变更/事件流的闭环可跑通；LLM prompt/JSON 解析路径已定义。
- 视觉：最小地图 + 角色点已可承载"实时观看"；正式版需双渲染器。

## 核心架构张力（设计必须回答）

1. **持久化 vs 常驻引擎**：世界线是核心资产，重启不能丢；但 LLM 引擎要按秒级 tick。存储层与引擎层必须解耦。
2. **世界线爆炸**：每条线一个完整世界快照会复制爆栈；纯 delta 链又难随机访问。需要快照/事件混合策略。
3. **LLM 非确定性**：同 prompt 两次结果不同。每条世界线必须有独立的 seed/上下文，日志必须记录完整 prompt+response+模型参数（可复现审计）。
4. **双渲染器**：2D/3D 并行是确定需求。渲染器只能消费投影，不拥有世界状态。
 renderers consume projections, never own world state.
5. **编辑器语义**："改任何东西"意味着编辑器操作的是可版本化的世界状态文档，而不是 ad-hoc SQL。
6. **部署形态**：本机单进程最简；云自托管不重写 → 引擎/存储/渲染的边界要能水平拆。
7. **原型已验证的假设**：非确定性下 fork 对比依然好玩（用户已实际游玩确认）。
