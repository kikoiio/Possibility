## 用户在场模型(用户提出,本讨论稿核心)

用户在世界中的存在是三态的,合并了此前"作者地位/镜头分配/追更体验"三个问题:

1. **不在场**(应用关闭/世界云端续跑):追更靠「新闻播报」——主要事件的播报式摘要。
2. **半在场**:可与任意角色对话(已定方向)。
3. **全在场(附身)**:用户是世界里的一个角色。~~两个变体~~ **已合并(2026-10-25 用户:B 包含 A,本质都是 B)**:统一为单一"附身"机制——用户可附身任意角色;无人在身时,该角色与所有角色一样由 LLM 驱动,**不存在引擎层的"用户专属角色"特殊路径**。"固定化身(A)"只是稳定使用同一具身体的用法,由使用习惯涌现。架构仅留两个 UX 开关:登录默认视角 = 上次身体(默认)/钉选某身体。
   - 镜头分配问题被此吸收:**镜头 = 用户当前(或上次)的视角**,不再是独立的导演机制。

## 已定方向(用户 2026-10-25 表述)

- **可和任意一个角色对话**。开放问题:对话是否"发生在世界时间线里"(占世界时间、给双方留记忆、旁人可见)——还是旁白式元提问(不入史、免费)。影响:契约(新 call kind)、引擎(对话事件的提交路径)、记忆(对话本身成为记忆)。
- **追更 = 主要事件新闻播报**。依赖事件重要度分级(与记忆系统的 importance 复用);播音视角=作者可见域的产物。开放:追更视图中能否回溯过去某点 fork(用户标待定)。
- **创世前史由用户与 AI 在创建时对话生成**:创世聊天 → WorldState + 前史记忆种子 + 角色设定,校验与 premise 一致。本质是编辑器的对话化。
- **驱动力/戏剧层(角色想要什么)**:暂无方案,**架构上解耦**以便持续改进。解耦缝建议(runtime 层的 story driver 可替换策略接口,v1 最便宜起步:Entity 开放字段放 desires/goals + prompt 约束尊重并演化——契约零改动),待讨论确认。
- **对话/实时交互的时间语义(2026-10-25 定)**:交互期间世界降速至真实时钟,降速前提醒用户,结束后恢复原速并提醒;降速窗口内到期 beat 的处理(抢占重生成 vs 交错提交)实现时定。

## 对话入史的影响分析与建议(2026-10-25,主 agent 提案,未定)

**提案:不是"同一种对话的两种模式",而是两个功能。**
1. **入世对话**:(需附身/化身)你以某个身份在世界时间线里说话。事件=对话文本+校验过的 ops+双方记忆(带 valence);天然可 fork("如果我没说那句话")。台词可以撒谎/记错——台词是叙述不是事实,只有 ops 和记忆走校验。
2. **记忆问询**:(观察者模式)对记忆系统的只读渲染——"甲眼中的火灾"=甲的 L1+L2+透镜,不入史、零事件、可作调试/审计 UI 复用。

**影响对比**:
| 层 | 入世对话 | 记忆问询 |
| --- | --- | --- |
| 契约 | 新 call kind('chat')+事件 kind+ChatRequest/Response DTO+SSE | 一个只读端点,无 revision |
| 引擎 | 事务提交(revision+记忆)+时间语义(见下) | 无 |
| 记忆 | 双方留记忆(带色),旁人可见可记 | 不留 |
| 成本 | 每轮=审计调用+存储 | 每轮=调用,无存储 |
| fork | **可 fork 对话本身**(产品级特性:两条线里你和甲说了不同的话) | 不可 |
| UX | 有重量;世界钟在走 | 随意、安全、像检查器 |

**入世对话的关键设计点(提案)**:
- 时间语义:进入对话会话时暂停该线(与会话期间暂停 beat 生成),对话事件按顺序提交为 revision;退出后重生成下一段 beat。备选更浪漫的"在场减速"——你在场时世界降到 1×,对话时长即世界时长(v2 再议)。
- 附身前置:入世对话要求"你是某人"(化身或附身);纯观察者只有记忆问询。这让在场模型成为承重墙:**想开口,先存在**。
- 对话中途可 fork(对话自身是 revision 链),未来可做"重谈这段话"的便利入口。

**反方账(如实记)**:入世对话引入暂停/抢占语义与预算压力,复杂度不低;若用户实际只要随口问问,记忆问询本已够用——但"可 fork 的对话"是平行世界产品的灵魂级特性,倾向保留。

## 连带影响(未定,需后续讨论)

- **记忆系统变成对话引擎**:角色回答只能来自其可见集,并带其情感透镜与当下讲法(L2)——问同一个问题,甲乙丙答案不同,这正是三栏对照的交互形态。
- **附身的可见性体验**:成为甲,就活在甲的可见墙内(亲身体验信息隔离);变体 B 还需定义"成为谁之后能看谁的记忆"。全知观察视图与第一人称视图是否可切换、如何切换——待定。
- **LLM 代玩用户化身(变体 A)的 autopilot 策略**:我不在时"我"做什么?这正是驱动力问题在用户化身上的特例,同样走解耦策略。
- **用户在场时世界是否照常推进**(对话/附身期间时间、计划、其他角色的 beat 如何处理)——待定。
- 对话/附身行为是否可 fork(它们如果入史,天然可 fork;元提问则不可)——与"回溯 fork 待定"同源。
