# 文本创世与实时 3D 研究

Wispiva 需要让作者以文本形成世界，并提供与模拟状态一致、具有吸引力的实时 3D 体验。正式架构采用参数化 solid 几何作为 v1 主渲染后端，voxel 作为第二后端和编辑辅助视图；下文的研究比较用于理解方法、质量证据与成本，不改变该架构分工。

文本生成 3D 的质量包含创作意图、结构、空间关系、可编辑性、视觉效果与运行成本。可执行程序、合理截图、有效网格或较低面数都不能单独证明成品好看、空间可用或适合目标设备。

资料阅读范围为 2026-10-24 至 2026-10-25，涵盖所引论文的方法、作者项目、仓库说明或官方 API 文档，不代表逐篇完整精读或全部源码审计。未运行所列外部项目、下载模型权重或调用生成服务；外部性能和费用是来源所报告的特定设置结果。采用工具前应针对具体制品核实版本、许可、运行条件与费用。

## 表示方式与生成方式

体素、三角网格和 Gaussian splats 是内容表示；LLM 生成程序、调用建模工具、场景布局系统、专门资产模型和完整空间生成是生成方式。表示和生成方式可组合。体素可以通过通用操作构造新形状，并不等同于固定模板；程序化几何也不预设低多边形或平涂风格。

| 路线 | 模型或系统产生什么 | 可研究的问题 | 主要限制 |
| --- | --- | --- | --- |
| 文本到体素蓝图 | 场景分区、材料、坐标区域、建筑蓝图或生成蓝图的程序 | 分层表达、空间布局、组合性和多视角修改 | 输出长度、空间关系和细部仍需结构检查；研究题材有限 |
| 文本到建模程序 | Blender Python、几何操作、材质节点或参数化部件 | 形状自由度、参数编辑、执行后反馈 | 程序能运行不等于造型好看、空间正确或能安全局部修改 |
| 场景规划与资产布置 | 场景图、物件关系、尺寸和位置约束 | 总体布局、语义关系、资产选择 | 资产覆盖、检索结果和费用受素材库与服务限制 |
| 文本／图像到物件网格 | 几何、纹理，有时包含重拓扑和动画工具 | 特殊物件生成及补充资产 | 尺寸、朝向、部件语义、碰撞、拓扑与性能需另验 |
| 语义部件生成 | 指定名称、功能或关系的分离网格 | 交互资产接口及部件级编辑 | 分离的部件不保证装配、蒙皮、运动和相互避让正确 |
| 文本／图像到完整空间 | 可浏览网格、Gaussian splats 或重建场景 | 场景整体生成与真实空间重建 | 可浏览或导出不证明稳定物件身份、交互、局部编辑和模拟状态贯通 |

## 文本构造、布局与程序化建模

- [T2BM](https://arxiv.org/abs/2406.08751) 使用 JSON 中间表示描述墙、屋顶与功能部件，避免逐块自然语言描写；[APT](https://arxiv.org/abs/2411.17255) 用程序生成 Minecraft 蓝图，并可依据多视角截图修订。方法支持分层场景表达，不证明任意题材都能自动生成高质量世界。
- [SceneCraft](https://arxiv.org/abs/2403.01248) 组合场景图、代码与视觉反馈；[LL3M](https://github.com/threedle/ll3m) 使用 Blender 建模程序并接受后续编辑指令。LL3M 仓库说明论文使用的服务已停止，源码与方法可作参考，但演示服务不能视作可用依赖。
- [Holodeck](https://arxiv.org/abs/2312.09067) 和 [SceneSmith](https://scenesmith.github.io/) 研究场景规划、物件关系和资产布置。布局规划适合构造总体组织，但只检索资产会受到资产库范围限制，需要和程序建模或生成资产结合。
- [Infinigen Indoors](https://arxiv.org/abs/2406.11824) 展示程序化资产、材质和约束布局能够形成写实室内场景。生成器本身需要开发，论文没有证明低成本覆盖任意题材。
- [ShapeAssembly](https://arxiv.org/abs/2009.08026) 及[代码](https://github.com/rkjones4/ShapeAssembly)以 cuboid、attach、squeeze、reflect 等组合操作表示参数化形状。同一程序可表达形状族并支持局部编辑；它是特定 DSL 与学习模型研究，不是通用世界生成器。
- [Procedura](https://arxiv.org/html/2608.26238v1) 与[仓库](https://github.com/SpatiaOS/Procedura)研究逐部件参数化 CSG：模型生成部件程序，用有类型的 mate 表达装配，由程序求解放置，再做编译、接口注册、穿插和连通性检查，最后由独立视觉 critic 定位问题并触发局部修订。论文消融支持规划、3D 反馈和修订有贡献；部分模型上的美学提升不显著，单次强模型也取得较高基准分。遮挡内部和精细接触可能逃过渲染视角，需要剖面、深度或网格查询。任务主要为机械物件，不是任意世界美术生成。
- [Scenethesis](https://research.nvidia.com/labs/cosmos-lab/scenethesis/) 结合语言规划、视觉引导、空间优化与复核。截图可以发现外观问题，但不能独立证明内部结构、碰撞或可通行性。

## 物件与完整场景生成

- [Meshy API](https://docs.meshy.ai/en/api/text-to-3d) 提供异步文本到 3D 资产接口，文档包含 GLB 输出、面数与拓扑控制。接口存在不代表资产满足室内结构、可交互性或统一美术方向。
- [TRELLIS.2](https://github.com/microsoft/TRELLIS.2) 是图像到 3D 资产管线，不是直接文本接口。仓库要求至少 24GB NVIDIA 显存；项目页秒级耗时来自 H100。两项信息分别描述运行条件和特定硬件成绩，不能代表普通本机耗时。
- [CubePart](https://about.roblox.com/newsroom/2026/05/cubepart-roblox-open-vocabulary-part-controllable-3d-generator) 可按语义名称生成独立网格部件，适合参考交互资产接口。官方说明刚体部件仍可能重叠，空间区分和有机角色蒙皮也有限；部件分离不等于装配或行为正确。
- [World Labs World API](https://www.worldlabs.ai/blog/announcing-the-world-api) 与[Tencent HY-World 2.0](https://github.com/Tencent-Hunyuan/HY-World-2.0) 提供完整空间生成或重建方向。能浏览、生成或导出不自动提供稳定对象身份、门窗状态、角色寻路、局部版本编辑或模拟状态连接；编辑粒度、许可、费用和模型版本需分别核实。

## 视觉质量与空间能力评测

[Creative Agents](https://arxiv.org/html/2312.02519) 和 [MineAnyBuild](https://arxiv.org/html/2505.20148) 可用于研究生成质量与失败模式。Creative Agents 的最佳受测组合使用扩散想象与 GPT-4V；论文仍记录简单建筑、循环生成的原始墙体、寻路破坏和体素重建问题。最佳展示案例只能证明可能性，不能代表常态成功率。

MineAnyBuild 测试了 **13 个多模态 agent**。论文报告 GPT-4o 总分 **41.02/100**；特定空间旋转测试中，受测模型的最佳正确率为 **26.7%**。这些结果属于论文任务、模型版本和评测协议，不能当作当前模型的永久排名。它们说明“模型会写建筑代码”并未解决空间关系问题。

质量检查应分别覆盖：

- 描述是否得到体现、用户是否觉得画面好看、材质与风格是否协调。
- 室内外结构和多视角是否一致；内部、被遮挡部位及不同镜头是否暴露缺失。
- 门窗、桥梁、部件连接、角色入口和活动空间是否成立。
- 文本修改能否保留未改内容；对象身份和位置能否与模拟状态一致。
- 目标设备的加载时间、CPU／GPU 帧时间、内存和显存，以及多视口开销。

视觉复核可帮助发现桥接错岸、入口遮挡或比例失衡。给复核模型的输入可包含多视角图、对象 ID 标记、尺寸、入口信息和结构诊断，让其返回引用具体对象的局部修改建议。截图不能替代空间查询；视觉模型也不应是唯一审美裁判。

## solid 几何与 voxel 构造

研究比较两种后端时，应让它们共享同一场景语义、输入意图、模型、预算和修订次数。比较维度是表达、生成、局部编辑和产品效果；面数、对象数和渲染批次须分开统计。

| 维度 | 参数化 solid 几何 | voxel 构造 |
| --- | --- | --- |
| 主要生成工作 | 设计部件、形状操作、接口和装配关系 | 设计区域、层、图案、材料和重复结构 |
| 形状表达 | 曲面、斜面、任意尺度细节和精确实体 | 栅格采样；细 voxel、台阶、斜面单元等能减轻阶梯感 |
| 易错点 | 布尔拓扑、穿插、悬空、连接和比例 | 输出过长、逐格空间错误、形体保守、细节重复 |
| 局部编辑 | 改参数或部件，重编译受影响节点 | 改区域或图案，重建受影响区块 |
| 与角色活动的连接 | 需另建碰撞、入口和导航表面 | 可由占用格派生候选碰撞和导航，但门、台阶及非立方体仍需语义 |
| 视觉特点 | 不受栅格轮廓限制；造型、材质、光照仍需美术投入 | 有统一视觉语言的潜力；轮廓、材料层次和光照决定细节效果 |
| 浏览器实现 | 需要实体内核或可靠网格操作、拓扑和面数管理 | 需要区块网格化、剔除、透明与材质处理；不应每个 voxel 都建一个 Three.js Mesh |

参数化 solid 不等于让 LLM 自由写任意三角形。受约束的部件配方由可靠几何工具执行，能保留参数并把空间检查和造型表达分开。[Manifold JS/WASM 文档](https://manifoldcad.org/docs/jsuser/)和[仓库](https://github.com/elalish/manifold)提供实体网格布尔与变换、manifold 输出保证及 JS/WASM 接口；这些保证不表示模型生成的部件好看，也不表示任意输入网格都会自动修复。

体素的组合性也不等于只能使用模板。区域填充、复制、旋转、对称、材料和自定义组合可以构造新形状。Minecraft 的创作能力还来自规则统一、低成本局部试错、表示与交互一致、成熟的工具和社区；视觉层次取决于材料色板、轮廓、细节尺度、光照、阴影、反射、雾与镜头，不只取决于方块数据。官方 [Vibrant Visuals](https://www.minecraft.net/en-us/article/minecraft-vibrant-visuals) 展示了在保留方块语言时增加体积光、阴影、反射和材质响应的方向。Minecraft 品牌和资产须遵循[官方使用准则](https://www.minecraft.net/en-us/usage-guidelines)。

Minecraft Java Edition 的持久化区块格式以 16×16×16 section 保存调色板和打包的方块状态索引；空或单一状态区域可紧凑表示。磁盘格式不等于渲染格式。[Chunk format](https://minecraft.wiki/w/Chunk_format)

## 体素渲染与性能参考

可扩展体素渲染器至少需要：

1. 区块保存单元数据，只生成可见表面；读取邻区边界以避免内部面和接缝重复。
2. 在 worker 中构建和缓存区块网格；局部编辑只标脏本区块及必要邻居，异步结果按版本提交，避免旧任务覆盖新编辑。
3. 按材质与透明类别组织批次，复用顶点、索引和实例数据，不能每格建立一个 Mesh。
4. 进行视锥剔除，评估区块可见图或 GPU 遮挡剔除；远景采用距离调度、加载预算或 LOD，透明体素单独处理排序。
5. 将平滑光照、AO、材质尺度和纹理重复纳入网格与着色设计。Greedy meshing 只适合合并顶点属性相容的共面区域，不能无条件减少所有面。

[Sodium](https://github.com/CaffeineMC/sodium) 是整体数据与调度系统的实现参考。其源码包含按 section 的网格构建任务、优先级调度与上传预算、邻区数据、区块可见性遍历、共享 quad index buffer 和区域绘制批处理：[网格任务](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/compile/tasks/ChunkBuilderMeshingTask.java)、[区块调度](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/RenderSectionManager.java)、[遮挡遍历](https://github.com/CaffeineMC/sodium/blob/dev/common/src/main/java/net/caffeinemc/mods/sodium/client/render/chunk/occlusion/OcclusionCuller.java)。它说明性能涉及调度、数据、可见性与批处理，不能只归因于 greedy meshing；它也不是可直接复制到浏览器的算法。

## 场景文档、检查与局部修订方法

可编辑场景通常需要稳定对象 ID、对象关系、几何配方和交互语义，并让后端产出可替换的渲染网格。本文把 `SceneDocument` 视为 Geometry Lab 的实验接口：solid、voxel 和外部资产可消费共享场景语义，但无需使用相同底层操作。

一个可检验的生成闭环可以包含：

1. **语义分解**：先形成区域、物件、部件、材质和连接关系，再构造局部几何。
2. **分层构造**：提供区域、挤出、旋转、曲线、阵列、开洞等通用操作；允许模型定义新部件和配方。
3. **确定性空间执行**：明确坐标、单位、方向、锚点、接口、占地和出入口；程序负责吸附、对齐、变换、尺寸及碰撞查询。
4. **结构验收**：检查操作有效、部件连接、开口存在、入口可达和活动空间足够，并以稳定 ID 返回诊断。
5. **可选视觉验收**：提供多视角图、对象标记、意图和结构诊断，由独立模型针对定位问题提出修订。
6. **保留与回退**：保存被接受的局部版本；失败回退至上一版本，未改部件不重新随机生成；预算耗尽时显示未完成内容。

[CraftUtopia](https://github.com/RGB-0000FF/CraftUtopia) 可参考按图样分区给 worker 并沉淀成功操作序列的做法。APT、T2BM 和 CraftUtopia 的共同思路是“模型提出计划，程序执行并提供可检查结果”，不是模型直接输出最终像素画面。

场景文档应保持物件身份与模拟状态的对应关系。门可以有开合状态、铰链和通行区域，网格可以由程序几何或专门模型生成；物件语义不依赖网格格式。已接受的产物、内容哈希、配方、生成器版本和参数可用于稳定回放；相同 seed 不保证跨模型重生同一结果。历史和分岔应复用已接受产物，只为变化部分创建新产物。

## 多模态、运行成本与可调用性

多模态模型可读取用户参考图，也可检查渲染结果。视觉反馈最好配合尺寸、对象 ID、入口与结构校验结果；仅凭截图可能无法区分遮挡、空洞和真实可行空间。普通角色推演可继续读取符号化世界信息，创世或大幅编辑时是否调用视觉模型需按能力与预算决定；不需要每个模拟节拍重新生成图像或整座世界。

SceneSmith 论文附录 O.5 表 18 报告 **179 个房间平均生成成本 13.98 美元、平均耗时 3 小时 26 分**。耗时来自 **8 张 L40S 同时生成 25 个场景**的吞吐评测设置，不是优化后的单场景交互延迟：[论文附录 O.5](https://arxiv.org/html/2602.09153v2#A15.SS5)。这组数据支持把生成成本和等待时间单独测量，不能直接据此确定 Wispiva 服务费用。

生成成本与日常运行成本应分别测量。用户浏览器负责实时 3D 渲染、相机和视觉动画；世界事实、历史与生成任务状态可以在不使用 GPU 的服务进程中维护。关闭观看页面不应被当作持续渲染的理由。分屏视图会产生额外 GPU 开销，不能假定共享资产便没有多视口成本。场景规模、设备、分辨率和视口数需要在验收条件中说明。

基本创世不应以安装 Blender、CUDA、Python 建模工具链或下载大型本地模型权重为前提。模型调用由用户配置的服务承担；Blender、专门网格生成和完整空间生成可作为独立选项，不能让普通世界运行依赖这些生成工具。浏览器的世界循环不应直接执行未经限制的生成代码。

渲染引擎不决定场景表示或美术风格。Three.js 的 [WebGPURenderer](https://threejs.org/manual/pages/webgpurenderer) 提供 WebGPU 和 WebGL2 后备路径，但既有着色器与新渲染路径的兼容性需要检查；[PlayCanvas standalone](https://developer.playcanvas.com/user-manual/engine/standalone/) 可脱离在线编辑器使用。无需仅因未来可能切换引擎而实现多套渲染后端。

## 实验解释边界

比较路线时应使用相同文字意图、模型、预算、返修次数、场景子集和检查条件，记录完整尝试与失败，并分别评价用户审美、空间结构、内部视角、部件编辑、角色通行、历史复用、加载、帧时间和资源成本。精选展示不代表常态成功率；模型强弱不同会影响结果，所谓“模型无关”只表示流程不绑定某一家模型的私有格式，不表示不同模型质量相同。

Geometry Lab 的具体样本、生成与局部编辑测量、静态网格统计和验收限制见[几何实验记录](../../prototypes/notes/research/geometry-lab.md)。这些受限样本能说明接口和检查闭环的行为，不代替开放题材、独立模型或目标 GPU 评测。

## 2026-10-27 原型补充：小场景的可读性与浏览器资源边界

《红发会》小起点把三个室内地点放在同一块紧凑地形上，并为当铺、地下室和银行使用不同的程序化陈设。一次真实浏览器截图发现，原先地点仍能通过几何检查，却因支撑地形半径和镜头距离过大而只占画面中央很小区域；这属于“空间合法但观察体验失败”。调整地点位置、房间尺寸、支撑半径和默认镜头距离后，三处现场在桌面与窄屏截图中都能读出，房间地板仍完整落在陆地上，角色绑定仍通过。

本次还发现一个集成层失败：Node 可以加载源码相对路径，但浏览器动态 import 会按照 URL 解析。`world-scene.js` 最初请求 `/prototypes/geometry/scene-compiler.js`，服务实际暴露 `/geometry/scene-compiler.js`，导致页面保留文字时间线而三维区域空白。修复后用 HTTP 资源检查、延迟浏览器截图和控制台异常采样确认画布存在，场景编译错误为空。该证据支持把“Node import、静态 URL、异步初始化后的画布”作为三项独立检查。

这次实验仍没有证明美术质量达到生产标准，也没有测量目标设备帧时间或多视口显存；无 GPU 的浏览器检查使用软件 WebGL 仅用于视觉和加载回归。下一步如继续提高画面，需要以多视角截图和设备性能数据为依据，避免只靠扩大几何或增加装饰解决问题。

## 2026-10-27 第二轮红发会视觉原型：从房间剖面到街区现场

首张红发会截图验证了前一轮定位：三间房间虽然通过空间和编译检查，画面仍像“地板加两面墙”的调试图。问题不是世界模型缺少地点，而是 solid 后端没有把地点语义映射到建筑部件、街面层次和材质响应。继续只调 UI 色板不能解决这个断层。

本轮保留同一份 `SceneDocument` 和同一套地点、角色绑定，按 `style.palette === 'victorian-archive'` 选择一组主题化 solid 配方：铺石广场、正面街道、砖墙、石材、橱窗、门框、当铺招牌、银行柱廊、地下拱口、台阶和路灯。它们是从 room 的名称、尺寸和位置确定性派生的渲染部件，不进入 world 事实，也不改变角色权限、资源或行动。通用 palette 仍使用原来的 room recipe，避免把红发会美术假设扩散到任意创世世界。

浏览器端原先调用 `createPlainMaterials()`，因此纹理材质在真实截图里被压成了纯色。现在浏览器使用已有的 `createMaterials()` CanvasTexture 材质，Node 编译和结构检查继续使用 plain 材质。这个分层保持了无 DOM、无 GPU 的验证路径，同时让浏览器端能看到砖、木、石材的尺度和粗糙度变化；纹理仍是轻量程序材质，不依赖下载资产或本地模型权重。

截图驱动的返修记录如下：完整屋顶板曾遮住房间和街面，截图显示三块棕色盖子压过了案件主体，于是撤回为檐口和开敞剖面；默认镜头从按陆地半径取景改为按内容包围盒取景，主题场景减少支撑地形的空边；第一版球形路灯像棋子，随后改为少量细杆、横臂和矩形灯箱。这个过程说明“几何合法”与“可读构图”需要分开的视觉回归证据。

当前截图证据 `.tmp/browser/rhl-street-v5.png` 显示：当铺和地下空间使用不同墙体与陈设，银行柱廊、暖色窗面、铺石地面和街灯可见；`#scene-host` 存在一个真实 canvas，`data-scene-error` 为空。该截图使用本机禁用 GPU 的 headless Chrome 和软件 WebGL，只能证明加载、材质、构图和运行时初始化，不代表目标设备帧率或显存预算。当前画面仍属于高辨识度原型，不应被记录为生产级美术资产。

## 2026-10-27 外部案例：单轮生成的动漫街区体验

对用户提供的 Bilibili 视频（标题为“吓哭了！Opus 5.5一轮生成绝美动漫樱花小镇！”）做了画面与公开提示词交叉检查。视频展示的是低机位、第一人称可漫游的动漫街区：道路、住宅立面、商店内景、神社、车站、站台和大量招牌／电线／路灯／树木共同维持同一视觉语言。公开整理的提示词把产物定义为单 HTML 的 Three.js 场景，要求模型使用程序化几何、Canvas 纹理、角色、灯光、天气、可交互相机和连续街区构图；这类展示不能证明它已经具备 Wispiva 所需的稳定对象身份、模拟绑定、导航和局部编辑能力。

该案例说明画面质量的主要来源是“主题化场景生成器”，不是让模型直接随机输出更多几何。模型得到的是一份高层视觉制作简报和明确的部件词汇，程序再把街道、建筑立面、门窗、招牌、树木、路灯、室内陈设和镜头展开为大量确定性细节。Wispiva 应保留 `SceneDocument`、world binding 和结构检查，把 LLM 的职责提升为场景规划与美术简报：输出主题、街区拓扑、建筑原型、部件集合、材质／灯光／镜头参数和少量稳定锚点，由本地配方库编译出可运行场景。

接入建议分三步。第一步增加主题内容包和 `styleBrief`，让同一地点可以选择街区、房间剖面或调查档案三种呈现；第二步为每个内容包增加建筑立面、道路、招牌、窗面、树木、灯具、室内陈设和第一人称入口等程序化部件，并从稳定对象 ID 生成装配；第三步在创世后生成多视角截图，先跑空间／通行检查，再让视觉复核只提出引用对象 ID 的局部修改。不要把视频中的单文件自由代码直接作为运行时世界，也不要让装饰几何成为第二份事实源。

《红发会》下一轮最有价值的实验是把三个孤立房间投影成一个可进入的案件街区：正面街道连接当铺、地下室入口和银行，地点仍绑定同一 world，地下室仍是可检查的隐藏空间；新增的是立面、招牌、窗光、檐口、路灯、铺石路、街角和第一人称镜头。这样能直接验证“程序化美术包”是否解决当前的丑，而不牺牲角色权限、行动、资源和历史语义。

## 2026-10-27 空间基底建议：采用 Minecraft 式可查询建造，不引入 Minecraft 运行时

Minecraft 式方法对 Wispiva 最有价值的部分是离散、可保存、可查询的空间状态：占用、材料、门洞、楼层、对象锚点、可通行面、区域和区块边界。它可以成为角色观察、寻路、碰撞和渲染的共同依据。Minecraft 的方块视觉和游戏运行时本身不是必要条件；Wispiva 可以用自己的小型空间基底，按区块保存结构数据，再由 solid、voxel 或主题资产编译成浏览器网格。

空间事实应分三层。第一层是语义图，保存 `place`、`room`、`street`、`portal`、对象身份和它们的关系；第二层是建造网格，保存地面、墙、门、占用、材料和高度等可执行空间；第三层是视觉投影，生成建筑立面、家具、招牌、植被、灯光和材质。`WorldState` 继续保存地点和影响模拟的事实，建造网格保存空间事实，`SceneDocument` 保存可重建的渲染投影；三者通过稳定 ID 绑定。

LLM 不应逐格输出整个世界，而应提出受限的建造操作或蓝图，例如创建房间、连接门洞、沿道路阵列建筑、在立面挂招牌、在指定区域铺设材料。程序负责吸附、尺寸、碰撞、通行、区块更新和对象身份。低层操作仍可落到 voxel，视觉细节由主题配方和程序化资产展开。

角色可以因此更可靠地知道“自己在哪里”，但这不是因为角色看懂了渲染画面，而是因为角色观察投影从同一空间基底读取当前位置、所在房间、可见对象、出口、邻近地点和已知地图。角色输入可以类似 `{ placeId, roomId, position, exits, visibleObjects, knownMap }`；权限层再删去尚未观察、被遮挡或属于他人私域的信息。当前位置是客观事实，角色对方向、距离和地图的理解仍可出错，并应通过记忆和观察更新。

因此建议 Wispiva 采用“语义图 + 小型区块建造网格 + 主题视觉编译器”的混合路线。它比当前只有地点和房间参数的模型多一层可执行空间，也比纯 Minecraft 方块世界保留更好的美术自由度。第一项实现应先覆盖地面、墙、门洞、房间、道路和对象锚点，再接入《红发会》的街区主题包；角色观察、寻路和第一人称镜头都从这份空间基底派生。

### 空间方位与角色记忆

“家东边有一家商店”应由确定性空间关系计算得到，再作为带来源的角色知识保存。项目需要固定世界坐标约定，例如 `+X=东`、`-Z=北`、`+Y=上`；建筑使用入口或语义锚点参与关系计算，不能只依赖装饰网格的随机顶点。给定两个对象的锚点或 footprint，程序计算 `eastOf`、`westOf`、`northOf`、`southOf`、对角方向、邻接和距离区间；路径系统另外计算“沿哪条路、走多久、经过什么门”，这与直线方位同时保留。

角色记忆不直接保存一个未经解释的坐标，而保存可追踪的空间信念，例如：

```json
{
  "kind": "spatial-belief",
  "reference": "home",
  "subject": "shop",
  "relation": "east-of",
  "distanceBand": "nearby",
  "source": { "type": "observation", "eventId": "obs-17", "revision": 4 },
  "certainty": 0.92
}
```

创世设定明确说角色知道时，可以用前史记忆种子写入；否则角色只有在看见商店、走到商店、查看地图或听到可信／不可信的对白后获得这条知识。模型输入只包含该角色已知的空间事实和当前可见关系，作者级空间索引不能直接进入角色上下文。建筑移动或分岔后，客观关系按新 revision 重算，旧记忆仍可保留为过时或错误的主观信念，直到角色重新确认。

现有 `world.places[].position` 与 `story.connections` 已经足够先实现 `spatial-relations` 查询和空间记忆来源；voxel／区块基底随后补充房间内部的门、遮挡、格子可见性、精确路径和局部建造。这样方位知识可以先进入角色 AI，而不必把完整建造系统和记忆系统绑成一次大改动。

### 推荐执行模型：工具驱动的建造循环

Wispiva 应让模型通过受约束的建造工具逐步修改 `SpatialWorld`，由工具负责执行、检查和返回结果，再由模型决定下一步。工具可以提供 `createRegion`、`createRoom`、`connectPortal`、`buildStructure`、`paintArea`、`placeObject`、`inspectSpace`、`renderPreview` 和 `repair` 等操作；底层可以使用 voxel 或区块数据，外观由主题配方展开。模型不直接写 Three.js、任意脚本或逐帧渲染逻辑。

每次工具调用都应是事务性的，返回 `ok`、`changedIds`、`diagnostics`、`revision`、`recipeHash` 和必要的局部预览。失败调用不留下半成品；成功调用记录为可回放的建造事件。工具必须提供宏操作，例如“沿道路生成三栋维多利亚店面”和“在房间北墙创建可通行门洞”，避免模型通过数千次低层调用消耗预算。低层 voxel 操作只用于局部修补和调试。

这种方式会降低模型对代码语法、Three.js API、布尔几何和资源释放细节的依赖，也能让较弱模型在统一工具约束下完成可验证的构造。模型能力仍影响布局规划、主题选择和返修判断，因此质量还需要内容包、结构检查和多视角视觉复核共同保证。工具循环的权威状态应是 `SpatialWorld`；`SceneDocument` 和 Three.js 网格从它派生，角色观察、寻路、碰撞和空间记忆也读取同一状态。
