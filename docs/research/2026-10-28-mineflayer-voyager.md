# Mineflayer / Voyager 对 Wispiva 的启发

更新时间：2026-10-26。

## 结论

不引入 Minecraft 运行时。Wispiva 应该采用 Minecraft 式的环境边界：世界状态可查询，角色只能通过有限动作改变世界，执行结果进入事件历史，验证器决定是否提交。渲染器和模型都只能消费这个边界。

当前代码已经有这四块的雏形：

- `observeResident()`：按角色隔离的观察。
- `sim.act()`：移动、检查、发言和其他行动的权威执行。
- `verifyDecision()`：检查模型决定是否基于当前观察且可执行。
- `ledgers`：每个角色自己的经历和记忆账本。

下一步把它们收拢成稳定的 `observe / propose / execute / verify / event` 契约，再在上层增加技能。

## 借鉴内容

Mineflayer 的关键价值是环境接口和插件边界：查询实体、位置、方块、物品、聊天和移动能力，调用者不需要直接操作渲染器内部。对应到 Wispiva，就是让模型只看到观察对象和动作 schema，不接触场景文档、存档文件或渲染细节。

Voyager 的关键价值是循环结构：根据当前状态选择任务，执行工具，读取反馈，必要时修正，再把成功过程保存成可复用技能。对应到 Wispiva，可以先做有限技能：

- `inspect-room`：检查当前房间尚未发现的线索。
- `ask-companion`：在同房间发问并记录听众。
- `follow-lead`：移动到与当前线索相关且可达的房间。
- `review-memory`：只整理本人已知事实和经历。

每个技能都必须声明前置条件、动作序列、允许的世界变化和验证器。技能库不能绕过角色知情隔离，也不能预写故事结果。

## 为什么不直接做 Minecraft

Minecraft 会提供成熟的体素碰撞、移动、区块和实体运行时，但同时会把项目带入方块世界、服务器 tick、区块存储、物品规则和大量渲染成本。Wispiva 当前的核心问题是信息差和可理解的叙事推进，四个房间的语义场景已经足够；直接引入 Minecraft 会扩大系统边界，不能自动解决 UI 和故事可读性。

因此当前路线是“Minecraft 式接口，Wispiva 式世界”：语义房间由模型生成，低层家具和连接由确定性编译器生成，角色通过受限动作推进，事件和记忆由运行时保存。
