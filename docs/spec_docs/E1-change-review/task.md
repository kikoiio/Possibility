# E1：变化发现、证据追溯与离开期间回顾 — Task Breakdown

## 目标与前置条件

目标是交付获批的 E1 用户路径：发现变化、打开事件、追溯来源与知识、理解可重建状态/证据缺口，并从有效检查点进入 F1 分叉。所有回顾读取均为只读，所有者权限与 K1 知识边界贯穿 API 和 UI。

前置条件：K1 与 F1 已在 B worktree 完成；E1 `spec.md` 和 `plan.md` 已批准。实施期间继续使用 B worktree，不在其他 worktree 重复修改共享世界状态契约。

## 阶段与任务

### T0：实施基线与契约确认 — 已完成

- 核对 `/return` 当前响应、`worldVisits` 迁移状态、事件/事实版本行为、`reconstructAt` 的支持域及 F1 确认入口。
- 冻结 API DTO、分页顺序和双水位语义：`eventCursor` 跟踪孤立/旧事件，`revisionVersion` 跟踪版本化命令/事实；标记已读只推进本次实际返回页面的水位。
- 明确关联优先级：显式命令/事实来源为直接关联；弱关系只作为可能关联且要带依据；无法关联时返回缺口。

交付：实现前契约与边界记录。T0 完成后再改共享 schema 和 routes。

### T1：数据库水位与后端证据读取 — 已完成

- 在 `api/src/db/schema.ts` 为 `worldVisits` 增加 `revisionVersion` 默认值，并新增单向兼容迁移 `api/drizzle/0035_e1_return_revision_watermark.sql`。
- 新增 `api/src/life/evidence.ts`，实现当前时间线的有界增量查询、事件与命令/事实显式关联、可读人物/地点信息、确定性高亮、事件证据详情、历史重建状态与 `gaps[]`。
- 复用 `versionAtTime`、`checkMoment`、`reconstructAt`，校验当前 timeline ID、事件模拟时刻和当前 `simNow`。任何不完整/不支持的重建只能返回缺口，不能返回可操作 fork 状态。
- 扩展 `api/src/life/routes.ts`：带游标/页大小的 `/return`、按事件 ID 读取证据详情、双水位 `/return/seen`。保留 world owner scope、auth middleware、约定动作与未读消息行为。
- 增加后端单测，覆盖 owner 授权、跨时间线及未来记录隔离、命令/事实链接、缺口、游标排序/翻页、同用户跨线隔离、并发写入不跳读、幂等推进。

依赖：T0。该阶段独占 `schema.ts`、迁移、`life/evidence.ts` 与 `life/routes.ts`，避免并发修改。

### T2：回顾与证据详情 Web 流程 — 已完成

- 在 `web/src/api/types.ts` 定义增量页、双水位、事件证据、事实/关联/未知及重建状态 DTO。
- 在 `web/src/api/client.ts` 实现回顾翻页、证据详情与双水位标记已读调用。
- 扩展 `web/src/components/world/LifePanel.tsx`：摘要、确定性重点项、事件列表、分页、空/错误/重试状态；既有约定操作和未读消息区域继续可用。
- 新增事件详情子组件，展示记录事实、可能关联、未知、来源命令、事实版本、人物/地点可读名称和缺口提示；私人正文仅显示 API 获准返回的内容。
- 标记已读仅提交实际加载并向用户展示的页末水位；在失败、翻页或组件关闭时保留安全的重试行为。
- 为 API 客户端和 UI 状态补充定向测试，覆盖分页、错误重试、权限空字段和事实/推断/未知的视觉区分。

依赖：T1 DTO 稳定后启动，避免 UI 与后端响应并行漂移。

### T3：有效检查点到 F1 的继续探索入口 — 已完成

- 在证据详情中仅对完整且覆盖指定时点的重建结果展示“查看该时点”及 fork 入口。
- 从详情携带 timeline、simTime、来源摘要和 `expectedSourceVersion` 到现有 F1 预览/确认流程；仍由用户检查动作并确认。
- 源版本过期时沿用 F1 冲突与刷新流程；不可重建、部分重建或越过当前模拟时刻时禁用操作并给出原因。
- 将此次入口接入 `WorldCanvasPage` 当前选中 timeline，不改变 demo/访客 fork 范围。

依赖：T1 的重建状态 DTO 与 T2 的证据详情交互。

### T4：集成验收与文档收尾 — 自动化验证已完成，少数专项验收待补

- 运行 API 与 Web 相关定向测试、类型检查/构建及迁移检查。
- 运行 E1 端到端旅程：登录 → 返回回顾 → 展开证据 → 标记已读 → 再次进入检查水位隔离 → 从可重建时点进入 F1；另覆盖缺失来源、权限拒绝、未来事件、过期版本和读取失败重试。
- 核对私信正文未进入公共事件、居民知识严格沿用 K1 证据；核对 E1 读取不产生新的命令、事实或记忆。
- 更新 `checklist.md` 逐项记录证据、通过/未通过/未验证状态；更新本文任务状态和实际变更文件。

依赖：T1–T3 集成完成。构建与浏览器验收错峰运行，启动前按本机规则核对 `MemAvailable`、`vmstat` 后续采样和 memory PSI；结束后关闭本任务启动且不再需要的临时进程。

## 依赖、整合与风险

- T1 是共享契约和数据基础，先完成 API 响应与迁移，再开展 T2；T3 依赖 T1 重建能力与 T2 交互入口。
- 双水位推进需在单个 D1 条件更新内验证本次可见水位，避免请求处理期间的新写入被误标已读。
- 同时间戳记录的稳定排序使用模拟时刻、记录类型和稳定 ID；分页令牌必须包含各自来源流游标，防止翻页重复或漏项。
- 历史重建成功只说明证据覆盖其声明的域，不代表能重建所有 UI 状态；响应与界面必须展示完整域和缺失域。
- 旧事件可能没有关联命令、事实、地点或知识，允许展示原记录并说明缺口，不写回补齐。
- 新增 migration 后应在隔离的本地 D1 数据库应用，并验证旧数据保持可读、`revisionVersion` 默认 0；禁止连接或改写用户真实世界数据。

## 完成定义

- E1 Spec 所有验收标准均有可复核的 API、UI 或端到端证据。
- 双水位、所有者权限、时间线/模拟时刻过滤和 K1 私人知识边界均经过验证。
- 有证据才可进入历史查看或 F1；失败与不完整证据都可读、可解释、可重试。
- `checklist.md` 标明每项结果和验证方式；未执行的检查如实保留为未验证。
