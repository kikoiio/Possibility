# K2：交谈渠道与空间事实一致 Plan

> 状态：完整 Plan 已获用户批准。

> 工作线：B——世界可信性与分叉。
> 依据：[spec.md](./spec.md)。

## 架构概览

- **渠道来源：** 把交谈渠道作为服务端上下文的一部分，而不是让模型从消息措辞中推断。人物页“打电话”使用普通聊天链路 `/api/conversations`，每个新聊天请求明确记录为电话；旧聊天请求渠道缺失时按未知处理。世界内现场交谈继续走 `/api/worlds/:id/scene`，由现有在场身份、当前地点、可回应居民和模拟时间校验确认为当面。
- **居民提示与工具：** 扩展 agent 上下文/提示，使电话模式明确用户为远程联系人；居民的位置仍以服务端当前状态为准。电话交谈上下文也传入状态与记忆工具执行边界，避免把联系者写成同地来访。现场交谈继续使用独立的 scene 提示与世界命令。
- **记录写入：** 每次聊天请求的渠道保存在请求记录中；电话消息正文留在原有私聊记录和获准参与者记忆中。现场场景仍保存为含在场身份的 dialogues/turns 与原子世界命令。活动和记忆更正沿用现有居民状态命令及可追溯来源；不得静默改写已保存历史。
- **一致性与失败：** 服务端从会话/入口读取渠道；客户端不能把普通电话请求伪装成现场会面。模型回复可以自然邀请来访，但只有现场入口通过位置校验才可产生共同在场记录。写入失败返回错误且不显示成功。
- **兼容：** 新增聊天请求渠道字段并用单向迁移兼容旧行；旧行设为 `unknown`，不回填推测渠道。K1 知识边界及现有普通聊天、在场交谈、访客/demo 路径按各自已有上下文继续工作。

## 核心数据结构与接口

- **渠道类型：** 定义 `CommunicationChannel = phone | in_person | unknown`。人物页普通聊天入口在服务端将新聊天请求固定标记为 `phone`；现场 `/scene` 继续由 `dialogues.kind=scene` 与 `scene_open` 命令表达 `in_person`，不接受客户端传入渠道覆盖服务端语义。
- **持久请求：** `chat_requests` 增加渠道字段，旧行默认 `unknown`，新电话请求由 `/conversations/:id/messages` 创建为 `phone`。渠道参与请求内容校验和恢复回执，确保重试沿用原语义；不回标旧 messages、旧 requests 或居民记忆。
- **模型上下文：** `ResidentPromptContext` 增加可选 `communication`，包含渠道及必要的对端信息；电话模式明确用户为远程联系人，并以服务端居民位置为准，不把用户加入在场者清单。无渠道的旧/内部调用按 `unknown` 处理，不提供现场会面语义。
- **工具运行态：** `ToolRunState` 继承本次通信渠道和居民当前地点。电话模式下 `update_state` 不接受由交谈请求触发的位置修改；`act` 和 `remember` 所生成的命令保留渠道来源元数据，方便审计并让后续修正可追溯。现场交谈的参与者、地点、时刻仍从服务端在场状态构造。
- **API 与兼容：** 普通聊天的创建、发送、恢复响应可返回已确定渠道；客户端不提交空间位置或参与者列表。`/scene` 的现场位置校验、幂等 requestId 和原子世界命令继续作为唯一现场会面写入路径。数据库仅新增带默认值的请求渠道字段，旧记录按未知读取。

## 模块设计

- **`api/src/db/schema.ts` 与新迁移：** 给 `chat_requests` 增加 `channel`，历史请求迁移为 `unknown`。不改 `conversations/messages` 的旧内容，也不重写居民状态、记忆或事件。
- **`api/src/chat/requests.ts`：** 扩展请求保留、读取和回执类型，把渠道纳入同 ID 重试校验；旧请求读取为 `unknown`。
- **`api/src/chat/routes.ts`：** `/conversations/:id/messages` 由服务端固定本次新发送为 `phone`，向 request reservation 与 agent turn 传递渠道；请求查询/恢复返回保存的渠道。建立/历史读取不从消息文本推断渠道。
- **`api/src/agent/context.ts`、`prompt.ts`：** 增加受限通信上下文。电话提示明确“用户通过电话联系，居民仍在服务端当前地点，邀请不等于用户接受/到场”；`unknown` 提示只承认已知信息、不构造现场相遇。`/scene` 继续使用 `api/src/agent/scene-prompt.ts` 的现场提示，不与电话提示混用。
- **`api/src/agent/loop.ts`、`tools.ts`：** 将渠道传入工具运行态；电话模式禁止该次 `update_state` 修改居民地点，并为行动/记忆类命令保留渠道来源。其余状态字段和合法的电话交流记忆仍可保存。测试覆盖模型尝试改地点、活动/记忆记录渠道和失败恢复。
- **世界状态提交层：** 在 `api/src/world-state/types.ts` 与命令投影/不变量中承载可选通信来源元数据；电话普通聊天不能创建带 visitor/现场 dialogue 关系的提交。`dialogues.kind=scene` 的居民资格、在场位置和原子提交校验保持为当面交谈约束。
- **Web 与测试：** `PersonDetail.tsx` 现有“打电话”入口与 ChatStream 继续使用普通聊天 API；扩展 Web 类型/客户端回执以显示渠道或可理解的请求失败。增加 chat route、agent prompt/tool、world-state invariant 与现场 scene 路由测试；旧聊天兼容测试确认历史仍可读且不被回填。

## 模块交互

1. **进入电话聊天：** 人物页创建或复用会话后发消息。API 校验会话所有者、世界和时间线；服务端将该次聊天请求标为 `phone`，客户端不能附带或覆盖用户地点、现场参与者或渠道。
2. **建立受限上下文：** API 保存带渠道的幂等请求，构造居民上下文并注入电话语境；居民当前地点来自该时间线服务端状态，用户不加入现场名单。模型可自然回应或邀请来访，但该邀请不会成为位置变更或当面会面。
3. **运行模型与暂存写入：** agent 的 `act`、`update_state`、`remember` 在本轮先暂存；电话模式拒绝 `update_state.location`，当前活动由服务端写为“通过电话与用户交谈”，不采纳模型提供的现场活动文本。记忆和事件附带电话来源。生成期间只流式显示文本，不提前向界面确认状态变更。
4. **成功提交：** 模型正常结束后，将本轮居民状态/事件/记忆投影、聊天回复和 request 完成状态作为同一数据库原子提交。事务成功后再发送完成与状态事件；重复 requestId 返回原回复/回执且不重复写世界记录。
5. **失败处理：** 模型中断、取消、校验失败或原子写入失败时，舍弃未提交的本轮暂存副作用，标记请求失败并显示重试/纠正入口；不得保留电话请求生成的现场位置、活动、事件或记忆。重试沿用现有 requestId 语义规则。
6. **现场交谈：** `/scene` 仍要求用户具有当前时间线的在场身份与状态地点；服务端按该地点筛选清醒且可交谈居民，再用 scene 提示词生成。至少一位居民回应后，现有 `conversation` 世界命令原子保存 turns、私有记忆和场景投影；校验或提交失败不落现场记录。
7. **历史与恢复：** 查询旧聊天仍返回原内容，但旧请求渠道保持 `unknown`；新请求状态、取消和恢复路径回传其持久化渠道。catchup 与自主模拟保持各自模式，不被误标为用户电话或当面交流。

- 修改 `api/src/agent/context.ts`、`prompt.ts`、`types.ts`、`loop.ts`、`tools.ts`，传递受限通信上下文，限制电话模式位置更新和活动文案，并暂存工具副作用；补充 agent prompt/tool/loop 测试。
- 修改 `api/src/world-state/types.ts`、`rules.ts`、`commit.ts`，支持一次电话回合的聚合居民状态命令及通信来源审计；补充原子写入失败和 telephone command validation 测试。
- 保持 `api/src/scene/routes.ts` 现场校验逻辑不变；扩展场景路由/世界状态测试，确保没有在场证据时不能创建当面会面，且合法现场交谈仍可完成。
- 更新 Web 的聊天请求类型/恢复回执；仅在现有“打电话”入口和错误反馈需要展示渠道/原因时修改 `web/src/pages/PersonDetail.tsx`、`web/src/components/ChatStream.tsx`，不新增渠道选择器。

### 技术决策

- 渠道由服务端入口绑定：普通人物页对话请求固定 phone，现场 `/scene` 由已校验的位置/参与者事实定义为 in_person；客户端不得设置在场关系。
- 渠道保存于每个 `chat_requests`，而非永久会话行；旧请求迁移为 unknown，新请求明确记录 phone，旧 messages/记忆不回填。requestId 重放必须保持同渠道、同负载。
- 电话回合先缓存工具副作用；生成成功后聚合为一个 `resident_state` 命令，并将命令投影、聊天回复与请求 completed 状态放入同一个 D1 batch。失败时丢弃暂存副作用；用户提交的原始消息和失败请求状态仍保留作重试依据。
- 电话模式不修改居民地点；活动由服务端写为电话交谈状态，避免模型输出把用户写成现场来访者。居民记忆/事件保留 phone 来源。电话内容仍按 K1 参与者知识规则存储和读取。
- 现场交谈继续复用现有 `scene_open` / `conversation` 原子命令、在场身份、居民资格、地点和时间校验；不引入额外模型调用来判断人在何处，不批量修复历史记录。
