# 核心闭环阶段 0 与阶段 1A Spec

## 背景

当前仓库已经具备世界生成、体素场景、兼容检查、修复预览和多种浏览器验收 fixture，但真实入口之间仍可能出现“生成后首次进入即遇到无效场景”“检查结果与保存结果不一致”“修复草稿无法提交或没有恢复路径”等断裂。`PLAN.md` 要求先冻结当前版本的可复查基线，再恢复阶段 1A 的场景可用性；历史截图和固定演示世界不能替代当前入口证据。

本轮只使用确定性 fixture/模型替身，完整复测 BB-01～BB-18，并记录注册后认领、访客时区、室内 3D、时间线显示等补充回归项。阶段 1A 只处理新世界的场景生成、规范化、最终兼容门禁、修复预览/提交和保底结果。

## 目标

- 产出当前版本的可复查基线证据：每个问题记录入口、身份、世界/时间线/空间、模拟时刻、响应状态、最终页面和证据位置；未处理的问题明确标为失败或未验证。
- 让新世界只有在最终兼容检查通过后才能保存并进入；该检查与用户可见的场景检查使用同一规则和同一结果语义。
- 当生成或编辑多次失败时，保存确定性的最小合法场景，并保留一条用户可以继续执行的修复/编辑路径。
- 让失败信息说明当前状态、是否已写入、是否可重试以及下一步动作，并保持重复提交和刷新后的状态可恢复。
- 为上述行为提供 API/单测证据和当前入口的浏览器/GUI 证据；重型浏览器验证在已授权的 GitHub Actions `ubuntu-24.04` 上执行。

## 功能需求

- **F1：当前版本基线复测。** 系统必须能够按统一矩阵复测 BB-01～BB-18，并额外记录注册后认领、访客时区、室内 3D、时间线显示；每项都记录入口、身份、世界/时间线/空间、模拟时刻、响应状态、最终页面和证据位置。
- **F2：证据可复查。** 基线与阶段 1A 验证必须产生脱敏的命令日志、响应摘要、页面/GUI 结果和版本信息；证据能区分通过、失败、未验证，并能关联到一次独立运行。
- **F3：场景生成规范化。** 新世界生成的场景候选必须经过统一规范化，明确入口空间、可进入空间、必要绑定和表现所需的结构；缺失或损坏的候选不能直接进入保存流程。
- **F4：保存前最终兼容门禁。** 世界保存和首次进入前必须执行与用户“场景检查”相同的最终兼容规则；只有完整通过的结果才能成为可进入场景，检查结果与保存结果必须引用同一版本和校验依据。
- **F5：可执行问题反馈。** 对无效入口、缺失空间、道路断裂、室内不可读、格式损坏和校验超时等情况，系统必须给出可理解的问题说明、影响范围、可执行的修改建议和下一步动作；不得只显示内部错误码或工程术语。
- **F6：修复预览与提交。** 用户可以基于当前场景生成修复草稿，预览前后差异并再次运行同一兼容检查；草稿只有在基准版本、规则、绑定和资产依据仍匹配时才能提交，提交后刷新和重新进入能看到已保存结果。
- **F7：确定性保底场景。** 当生成或编辑达到预设失败上限，系统必须保存一个确定性、可进入且通过最终兼容检查的最小场景，并明确标识其为保底结果，同时保留可执行的后续修复/编辑入口。
- **F8：失败恢复与幂等。** 生成、检查、修复和保存请求在断流、刷新、重复点击、超时或网络失败后必须可查询、可重试或可恢复；成功重试不得产生重复世界、重复场景版本或覆盖更新后的场景。
- **F9：新世界连续路径。** 从创建新世界开始，用户必须能够完成“生成 → 检查 → 修复或保底 → 保存 → 首次进入 → 刷新后再次进入”；每个分支都能观察到明确的成功或恢复结果。

## 非功能需求

- **N1：可重复性。** 在相同 fixture、输入、规则版本和资产清单下，生成、规范化、兼容检查和保底结果必须产生相同的候选摘要、问题代码集合和内容哈希；时间戳、随机请求标识等运行元数据不得改变业务结论。
- **N2：数据与权限边界。** 检查、修复和保存只能作用于已授权的世界、时间线和空间；客户端提交的绑定、版本和权限字段不能覆盖服务端解析结果；失败和重试不能泄露其他世界内容。
- **N3：有界资源消耗。** 场景校验、修复规划和保底生成必须有明确的工作量、超时和取消边界；不得因单个坏场景、重复点击或浏览器断开而无限重试或持续占用模型/Worker 资源。
- **N4：状态原子性。** 场景内容、版本、兼容依据和基线状态的更新必须保持一致；并发提交、过期草稿和重复请求只能产生一个可追溯结果。
- **N5：可观测性与脱敏。** 每次验证至少记录规则版本、资产/绑定摘要、工作量、停止原因、模型替身调用次数、最终保存状态和失败原因；日志和截图不得包含真实密钥、会话凭证或未授权的完整隐私内容。
- **N6：入口兼容性。** 新世界和修复入口在桌面以及 `485×724`、`390×844` 视口下可操作；主要按钮、错误说明、重试入口和场景预览不被裁切，键盘焦点与触摸操作可达。
- **N7：验证隔离。** 浏览器/GUI 验证使用独立数据库和临时目录，单次只运行一个重型 GUI 实例；云端工作流上传的仅是必要证据，不改变用户现有环境或远端持久世界。
- **N8：向后兼容。** 既有合法演示世界、时间线场景读取和现有兼容检查测试继续通过；本轮新增行为不得要求恢复已删除的历史体验材料。

## 不做的事

- 不在本轮修复 BB-02～BB-18；阶段 0 会记录它们的当前结果，但只有 BB-01 相关的场景生成/兼容/修复链进入实现。
- 不实现阶段 1B 访客保存与认领、阶段 1C 世界投影一致、阶段 2 记忆/时间/交谈一致、阶段 3 Fork/比较/窄屏完整体验或阶段 4 显示层统一。
- 不调用真实模型、真实账号或真实远端世界；本轮只使用确定性 fixture/模型替身。也不引入新的模型供应商、密钥或训练流程。
- 不实现学习型世界模型、WFC/Rive/Recast/glTF 优化、复杂社会模拟、更大地图或新的 Fork 类型。
- 不以历史截图、旧报告或固定演示世界的通过结果替代当前版本的真实入口证据。
- 不进行生产部署、远端持久数据迁移或删除用户/其他任务创建的资源；GitHub Actions 只运行隔离的验证工作流并收集必要证据。
- 不恢复已删除的历史体验材料，也不重写与本轮场景可用性无关的现有工作区改动。

## 验收标准

- **AC1（对应 F1）：** 运行阶段 0 基线流程后，产物包含 BB-01～BB-18 共 18 行，以及注册后认领、访客时区、室内 3D、时间线显示等补充项；每行都有入口、身份、世界/时间线/空间、模拟时刻、HTTP/页面结果、状态（通过/失败/未验证）和证据路径。
- **AC2（对应 F2、N1、N5）：** 使用同一确定性 fixture 重复运行两次，场景候选摘要、问题集合、规则/资产摘要和内容哈希一致；产物包含版本、调用次数、停止原因和脱敏检查结果，且不含密钥或会话凭证。
- **AC3（对应 F3、F4）：** 对包含无效入口、缺失空间、道路断裂或室内不可读问题的候选执行保存尝试，保存被拒绝；用户检查与保存前最终检查返回同一问题集合、场景版本和校验依据，未通过场景不能首次进入。
- **AC4（对应 F5）：** 浏览器中每类已支持问题都显示可理解的原因、影响范围、可执行修改建议、是否已写入、是否可重试和下一步按钮；页面不要求用户理解内部错误码、UUID 或资产字段。
- **AC5（对应 F6、N2、N4）：** 对当前场景生成修复草稿后，预览能显示候选变化并重新检查；基准版本、规则、绑定或资产依据过期时提交被拒绝并要求重新检查，依据未变时只产生一个新场景版本，刷新后可读到该版本。
- **AC6（对应 F7）：** 连续触发预设的生成/编辑失败上限后，系统保存确定性的最小合法场景；场景检查通过、首次进入成功，页面明确这是保底结果并提供后续修复/编辑入口。
- **AC7（对应 F8、N4）：** 在断流、刷新、超时、重复点击和网络失败后查询同一请求，能得到已完成、失败可重试或可恢复状态；重复成功重试不会生成第二个世界、重复场景版本或覆盖较新的版本。
- **AC8（对应 F9、N6）：** 在桌面、`485×724` 和 `390×844` 视口完成“创建新世界 → 生成 → 检查 → 修复或保底 → 保存 → 首次进入 → 刷新后再次进入”；每个分支都能看到明确成功或恢复结果，主要控件可通过鼠标、触摸和键盘操作。
- **AC9（对应 N2）：** 使用不匹配的世界、时间线、空间、绑定或权限提交检查/修复/保存请求时，服务端拒绝请求且不写入任何场景内容。
- **AC10（对应 N3）：** 对超出工作量或超时边界的场景，流程在规定边界内结束并显示可重试或保底路径；取消后没有继续运行的验证/模型替身任务。
- **AC11（对应 N7）：** GitHub Actions `ubuntu-24.04` 工作流在隔离数据库和临时目录中串行完成浏览器/GUI 矩阵，上传日志与截图证据，并在结束时确认临时服务和临时资源已清理。
- **AC12（对应 N8）：** 现有合法演示世界的读取、既有场景兼容单测、API 构建、Web 构建和受影响的浏览器测试继续通过；阶段 0 记录的其他 BB 项不因本轮改动被伪装为已修复。
