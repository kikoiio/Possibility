## Base and grafts

Use candidate A as the base. Its home relation and visit mutation boundary are smaller and make authorization provenance harder to misuse. Its private `TimeContextSource` does not expose rows, while the mutation path needs only the principal and an authorized context. Its scene design also assigns the synchronized root-timeline/legacy pointer statements to a real owner and says those statements remain in the original D1 batch.

Graft from candidate B the separate `useLegacyWorldComparison` workflow if the U4 page-size predicate or lifecycle ownership warrants extracting it. Preserve its responsibility for right-side reads, request generations, URL mode/right synchronization, and split presentation inputs, but keep the hook API as small as implementation evidence allows. Also graft B's explicit public-versus-guest route matrix and import-boundary check for scene internals.

Reject B's exported row-bearing `ReadableTimeTarget` shape. Keep target authorization as a private constructor and pass only data required by the authorized operation; do not let downstream code depend on raw Drizzle rows or a second copy of access policy. Reject ordering static endpoints before generic parameter routes as an authorization strategy; route matching and middleware ownership should be proven in a harness, not encoded as a fallback policy. Reject any permanent old/new scene API aliases; a compatibility barrel is acceptable only for the bounded migration and must then lose obsolete aliases.

## Source contract checks

- **Version fields:** `api/src/worlds/time-context.ts` sets both `stateVersion` and `revisionVersion` from `universeRevisions.version` (defaulting to zero). `api/src/worlds/status.ts` and `web/src/api/types.ts` both currently declare both fields. Retaining them on this DTO is correct; do not equate `revisionVersion` in unrelated world-fact, event-cursor, or scene-history contracts with this alias.
- **Visit authorization:** `api/src/life/visit-sessions.ts` currently checks only that the timeline belongs to the supplied world before reading or mutating visit rows. `contextFor` performs world access validation after writes. Both candidates correctly identify the demonstrated unauthorized mutation and call for authorization before replay lookup/session reads and writes, including leave-with-no-session. Preserve current validation, response status, replay, and no-op semantics around that correction.
- **D1 atomicity:** `api/src/scenes/repository.ts` batches timeline head reservation, revision insert, head update, legacy main-scene writes, proof guard, and compatibility completion in one `db.batch`; legacy commits similarly batch revision/current pointer, baseline/request completion, guard, and `legacyMainSceneStatements`. Repository extraction must keep all statements in the same batch and in compatible order. Candidate A's statement-factory bridge is compatible if it only builds statements and never executes its own batch. Candidate B states the invariant but should graft A's explicit bridge ownership. Existing unique timeline revision/request indexes are present in `api/src/db/schema.ts`.
- **Auth ownership:** `api/src/index.ts` mounts multiple routers at `/api`, and `chat/routes.ts`, `timelines/routes.ts`, and `life/routes.ts` currently use router-wide `use('*', authMiddleware)`. `worlds/routes.ts` also uses a router-wide scoped middleware. The design must move protection to routes/subrouters that own each path, retaining guest behavior in routes that currently allow guests. Merely reordering the root mount list would leave the registration-order dependency.
- **Dirty worktree:** At review time the tree contains numerous modified and untracked phase 2B files plus `.audit/` artifacts. Preserve them as the baseline. The future implementation must not reset, clean, overwrite, or report them as newly introduced. Record before/after state accurately.
- **Cloud permission:** Both candidates describe GitHub Actions/cloud execution as authorized. That statement inside candidate text is not user permission. The supplied machine rules require telling the user which cloud service, purpose, and permissions are needed and obtaining approval before invoking it. The current cross-judge request explicitly prohibited cloud actions, so none were invoked.
