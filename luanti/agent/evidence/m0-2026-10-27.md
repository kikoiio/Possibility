# M0 证据：Luanti 服务端 agent 的最小闭环（2026-10-27）

M0 的退出条件是三条，本文件逐条给证据：

1. 可重复启停；
2. agent 确实每个 server step 都被引擎推进；
3. 失败有明确原因，而不是静默消失。

**本文件只证明这三条**。它不证明 agent 有智能、不证明 LLM 能接、不证明规模上限，也不证明有玩家时同样成立。边界见文末。

## 环境与产物

- 机器：本机 Ubuntu，14 GiB RAM。运行前 `MemAvailable` 约 8.7 GiB，`/proc/pressure/memory` 全零，`/tmp` 使用 2%。
- 运行方式：**零 sudo、零系统包安装、零 Java**。`runtime/bootstrap.sh` 把 11 个 deb 下载后 `dpkg-deb -x` 解包成项目内运行时（`.runtime/`，可由脚本重建，不入库）。
- 被测产物（哈希取自 `agent/evidence/*.report.txt`，与运行时 `manifest.sha256` 一致）：

| 产物 | sha256（前 16 位） |
| --- | --- |
| `luantiserver`（Luanti 5.10.0 / LuaJIT 2.1） | `d6c1d25c67f4c3d2` |
| `agent/mod/society/init.lua` | `dcbed98fd0a0bfe0` |
| `agent/mod/society/policy.lua` | `c69252d24452cceb` |

启动时 mod 自己把这两个哈希写进日志（`SOCIETY artifact`），因此下面的行为数字能对应到具体的源码版本。

## 怎么跑

```bash
runtime/bootstrap.sh                          # 幂等：缺什么补什么，已下好的 deb 不重下
agent/run.sh --label m0 --repeat 2            # 5 agent，各 10 次决策，跑两次比对
agent/run.sh --label m0-n20 --agents 20 --decisions 8
agent/run.sh --label m0-stop --decisions 0 --seconds 15   # 不自动关服，走 SIGTERM
agent/run.sh --label m0-negative --set society_spacing=64 \
  --expect-fail agents-lost-after-spawn       # 反向用例
```

`run.sh` 一次只允许一个服务端在跑（发现已有 `luantiserver` 会拒绝启动），这与基准测量的顺序口径一致。

## 结果

| 场景 | 停止方式 | 用时 | 峰值 RSS | 每区间被推进 | 最低 step/s | 校验 |
| --- | --- | --- | --- | --- | --- | --- |
| m0.run1 / run2（5 agent，各 10 决策） | 自行关服 | 23 s | 45 MiB | 5/5 | 11.08 | PASS |
| m0-n20.run1（20 agent，各 8 决策） | 自行关服 | 19 s | 46 MiB | 20/20 | 11.08 | PASS |
| m0-stop.run1（5 agent，SIGTERM 停止） | 外部 SIGTERM | 15 s | 45 MiB | 5/5 | 11.08 | PASS |
| m0-negative.run1（spacing 超出 forceload 范围） | 自行关服（检测到失败） | 5 s | 44 MiB | — | — | PASS（失败被检出） |

实时基准 11.1 step/s。三次正常运行的 step 率都在 11.08–11.12，即服务端没有掉出实时。
20 agent 时的账：160 次决策、6 个标记、16 次接触。原始日志见同目录 `m0*.log`，逐项报告见 `m0*.report.txt`。

### 1. 可重复启停

```
[m0.run1] self-shutdown, 23s, 峰值 45 MiB, 事件 73 行
[m0.run2] self-shutdown, 23s, 峰值 45 MiB, 事件 73 行
[m0] 可重复性: run1 与 run2 的确定性事件序列完全一致（73 行）
```

比对的是 `m0.run1.events` 与 `m0.run2.events`：两次运行各自从空世界开始，逐行比对
`SOCIETY banner|artifact|forceload|spawn|check|ev=|verify|summary|done` 全部一致。

**这个"一致"是有边界的，不能夸大**：比对的行里**不含**墙钟、`steps_per_sec` 与 `t=` 统计行——
真实时间本来就不可复现。事件序列一致，靠的是两件设计：

- 决策用固定种子的 LCG，不用 `math.random`（后者受引擎与调用顺序影响）；
- 决策由一个 `globalstep` 驱动、**按 agent id 排序**依次执行，而不是写在每个实体的 `on_step` 里。
  引擎遍历活跃区块的顺序不保证稳定，写在 `on_step` 里日志交错就会随机化。

停止路径单独测过：`--decisions 0` 时不自动关服，由 `run.sh` 发 SIGTERM，服务端仍写出完整的
`SOCIETY verify` 与 `SOCIETY shutdown` 账（`m0-stop.run1.log`），进程退出经 `kill -0` 复核。

### 2. agent 确实每步被推进

证据有两层，缺一不可：

- `SOCIETY stats ... stepped_delta=5/5`（20 agent 时 20/20）：每个统计区间内，每个 agent 的
  `on_step` 计数都在增长。**注意这只证明实体在 step，不证明无玩家时它会被 step——后者靠下面的 forceload。**
- `SOCIETY stats ... steps_per_sec=11.08~11.12`：globalstep 计数/墙钟，服务端维持在实时。

无玩家时实体默认不会被 step：必须先 `forceload_block`，日志里的 `SOCIETY forceload blocks=25/25` 是这一步。
而只有 forceload 还不够：**必须在 `core.emerge_area()` 的 `calls_remaining == 0` 回调里再生成实体**。
顺序写反了就是下面这个反向用例。

### 3. 失败有明确原因（反向用例）

把 `society_spacing` 设成 64，agent 的生成点落到 forceload 范围（`bound=32`）之外，这是"静默消失"
那一类失败的复现：

```
SOCIETY spawn count=5 ok=5 spacing=64 bound=32
SOCIETY check stage=spawn alive=1 expected=5 ok=false
SOCIETY fail=agents-lost-after-spawn alive=1 expected=5 hint=emerge-race-or-active-block-purge
SOCIETY summary spawned=5 alive=1 decisions=0 rounds=0 marks=0 meetings=0 actions=...
SOCIETY done result=fail reason=agents-lost-after-spawn
```

三点值得记住：

- `add_entity` 五个全部返回**有效对象**（`ok=5`），一个错都不报；
- 1 秒后只剩 1 个——活下来的那个恰好是生成点 `(0,1,0)`、落在范围内；另外四个在 `|x|` 或 `|z| = 64`，被清掉；
- 程序自己发现了这件事，说得出比预期少几个、并给出原因与提示。

`run.sh --expect-fail <reason>` 就是为这种用例准备的：**检测到失败才算通过**，
静默通过反而判 FAIL。没有这个反向用例，"失败有明确原因"只是一句自述。

### 4. 世界真的变了（不是只改了自己的变量）

计数器是 mod 自己的账，不是世界的账。关服时回读地图核对一次：

```
SOCIETY verify marks_counter=2 marks_in_world=2 ok=true          # m0.run1
SOCIETY verify marks_counter=6 marks_in_world=6 ok=true          # m0-n20.run1
```

`marks_in_world` 由 `core.find_nodes_in_area()` 扫地图得到，与 mod 自记的标记数一致。
agent 的行为在世界里留下的是真实的方块，不是日志里的字符串。

### 5. 闭环长什么样（M0 用的桩策略）

一次决策 = `observe → policy.decide → apply → 事件`，全部走同一份代码路径；策略是
`policy.lua` 里的确定性桩（`m0-stub-1`），**没有 LLM**。规则与观察因果绑定，不是随机数：

| 观察 | 意图 |
| --- | --- |
| 手上还有未走完的目标 | `advance` 走一格 |
| 附近一个标记都没有 | `mark` 在身前放一个标记 |
| 附近标记 ≥ 3 | `wander` 另选目标点（太挤） |
| 最近的邻居还没接触过 | `approach` 走到它身边 |
| 连续两次无事可做 | `wander`（不许原地不动） |
| 其余 | `inspect` 观察并写进记忆 |

5 agent 的 50 次决策分布：`advance:26, approach:8, inspect:10, mark:2, wander:4`，产生 5 次接触。
日志里能看到因果链是完整的。下面是 `m0.run1.events` **第 29–52 行中属于 delta 的逐字摘录**
（原文件里各行之间还夹着其余 4 个 agent 的同一轮决策，这里只摘 delta 的行，不改变任何字段）：

```
SOCIETY ev=approach agent=3 persona=delta target=0 at=-6,1,-8
SOCIETY ev=move agent=3 persona=delta to=-8,1,-6 remaining=2 why=en-route
SOCIETY ev=arrive agent=3 persona=delta at=-8,1,-6
SOCIETY ev=approach agent=3 persona=delta target=0 at=-6,1,-8
SOCIETY ev=move agent=3 persona=delta to=-6,1,-6 remaining=2 why=en-route
SOCIETY ev=arrive agent=3 persona=delta at=-6,1,-6
SOCIETY ev=meet agent=3 persona=delta with=0 persona=atlas at=-6,1,-6
SOCIETY ev=meet agent=3 persona=delta with=4 persona=ember at=-6,1,-6
```

读法：`target=0` 是邻居的 agent id（atlas），`at=` 是程序为它选的落点——邻居的**相邻格**，
不是邻居身上。delta 分两步走到落点、`arrive`，随后 `meet` 记下与 atlas 的接触；
下一轮它发现还有没接触过的 ember，再走一步并接触。
接触是**执行结果反馈进记忆**，不是决策本身：`settle_contacts()` 在动作落地后按实际距离判定。

## 结论

M0 的三条退出条件都有本项目自己的、可重复运行的证据：

- **能起停**：自关服与 SIGTERM 两条路径都留下完整账，进程退出经复核；同配置两次运行事件序列逐行一致。
- **每步被推进**：`stepped_delta` 等于 agent 数，step 率 11.08–11.12（基准 11.1）。
- **失败说得清**：反向用例里 5 个实体全被静默清掉，程序自己检出并给出原因。

同时确认了 C 路线的现实形态：agent 是**服务端 Lua 实体**，无客户端、无玩家视角、无需 Java 与账号。

## 边界（不要把上面的数字读成更多东西）

- **没有 LLM**。决策是 `policy.lua` 里的确定性桩，只有 6 条规则。这里测的是环境与闭环，不是智能。
- **没有持久化**。`static_save = false`，每次运行从空世界重新生成 agent；快照与重置是 M3。
- **没有客户端连接，也没有玩家在场**。`max_users = 8` 但全程零连接。
- **规模只到 20**。容量阶梯是 M1；本文件里的 20 agent 只是"不是 5 agent 的偶然"。
- **引擎是 5.10.0**，不含上游 2025-04-08 的 k-d 树空间索引；单次运行、单配置、未做长时间稳定性测试。
- **只在本机跑过**。没有云端任务，也没有跨机器复现。
