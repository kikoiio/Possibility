# 几何对照原型观察

日期：2026-10-24。代码与结论都是一次性实验，不是正式架构或美术验收。

## 做了什么

在 `scratch/geometry-lab` 手写同一座临水藏书屋的两个确定性配方：参数化通用几何与 0.42 单位体素。两者共享尺度、材质、光照和交互界面，可切换全景、室内、细节视角与分屏；支持更换门廊和桥头的局部编辑。

没有调用模型或付费服务。第一轮为两个手写配方；本轮已由同一个 `SceneDocument` 驱动两个确定性后端，但没有模型生成实验，因此仍不能比较 LLM 在两条路线上的生成成功率。

## 已实际观察

- 通用几何：斜屋顶、弧桥、圆形观景台、圆柱家具和自由轮廓容易表达，局部部件结构清楚；树冠与墙体仍有基础图元拼装感，室内视角需要避免近处遮挡。
- 体素：整体材质语言更统一，细节密度更高；当前配方让桥、屋顶和树冠显得过密、过于锯齿。它不是 Minecraft 上限的展示。
- 室内：两套场景都有真实地板、墙、书架和桌椅，而非只有外观。初始通用几何镜头被门板挡住，调整相机后可观察室内；尚未实现角色行走和碰撞导航。
- 编辑：门廊和桥可以替换为观景台；保留地形对象，不借局部编辑重建所有内容。现在由 `SceneDocument` recipe hash 推导脏部件，`compileSceneParts` 只替换受影响节点并释放旧 geometry；`scene.test.mjs` 锁定了稳定部件引用与 rebuilt part IDs。
- 浏览器：完成桌面 1440×1000、手机 390×844、分屏、室内与编辑截图检查；无页面异常，手机无横向溢出。

## 构造数据

以下为初始版本 B（观景台）在当前实现中的静态产物统计。它不是 LLM 生成成本，也不是跨设备性能基准。

| 指标 | 通用几何 | 体素 |
| --- | ---: | ---: |
| 三角面（含实例展开） | 21,550 | 115,058 |
| Mesh / InstancedMesh 批次数 | 246 | 34 |
| 实例数 | 648 | 9,582 |

这组数据反驳了“面数更少就必然更快”：通用几何面数少但独立网格多；体素面数多但实例化批次少。阴影、像素填充、透明、驱动与 CPU 提交都影响结果。

自动观察使用一个本机无头 Chrome、ANGLE SwiftShader 软件 WebGL 和 2048 阴影图。分屏截图时界面移动平均约 89ms/帧，不应把该数字当成硬件 GPU 帧率，也不应把首次截图的默认 16.7ms 当成实测成绩。后续必须在真实目标 GPU 上分别记录 CPU/GPU 时间。

## 对选型的影响

原型没有证明哪条路线获胜。它让下一项关键实验更明确：不要继续只比较手写 demo，而要实现一个足够小的共享语义场景子集，让相同模型和预算分别生成两种配方，比较陌生场景的成功率和局部修订质量。

通用几何不能停留在 primitives 拼房子；需要部件级细节、曲线/曲面、可靠几何操作和视觉反馈。体素不能停留在实例化方块；需要细部形状、表面网格优化、材料尺度与非整格部件，否则密度和性能会随世界规模快速上升。

## 生成对照实验：管道就绪与会话模型首轮

2026-10-24。新增 `generate-experiment.mjs` + `experiment-intents.mjs`：6 个陌生场景意图（每个附手工参考解，证明在子集内有可行解），同一"模型"逐个生成语义 SceneDocument → 结构 + 空间校验 → solid/voxel 双后端编译与探针 → 每意图一次"把门廊加宽 1.2 米"局部修订，用语义 diff 推导期望脏部件，检查增量重建是否越界。报告写入 `.tmp/geometry-lab/generate-experiment/`。

- 管道验证（mock，返回参考解）：6/6 文档校验通过、双后端编译成功、修订均恰好重建 `porch`、零越界重建；`mock-broken` 意图（0.7m 入口）被正确拒绝并带结构化诊断。`scene.test.mjs` 回归 8/8。
- 会话模型首轮（`--generated=generated/glm-session`，每个意图只取首次输出，不返工）：同样 6/6 全绿，包括双岛长桥、高台、六树、10×7 大厅等参数各异的场景；修订均精确落在 `porch`。
- 证据边界必须写清：这不是外部模型成功率。会话模型与参考解同源（都出自本轮作者），且约束由作者自己写进 prompt，测的是"管道可被强模型走通"的上界，不是冷启动成功率；会话模型也没有真实 API 的格式抖动与延迟。
- 结论与下一步：共享 SceneDocument + 确定性后端的设计已可被强模型完整走通，约束清单（入口净空、岛内落位、树/桥净空、桥端高差、坡度）是可学习、可校验的。下一步才是真正的成功率实验：接入独立模型（本机 key 或 Actions secret）跑同一组意图，并加入"校验失败 → 带诊断返修一次"的第二轮，观察诊断信息能否换回成功率。

验收边界：意图与子集都偏"临水建筑"，不代表任意题材；修订指令只有一种；编译统计是 CPU 数学，不代表目标 GPU 性能。

## 村庄级生成：子集扩展 + 模糊 prompt 首轮

2026-10-24。按"用户不会给详尽 prompt"与"场景至少到村庄"的要求做的第二轮扩展。

- 语义子集新增 `kind=house`（民居，与 library 同构：bounds/entrance(front)/roof(gable)）与 `kind=path`（石板路：2–64 个 [x,z] 点 + width）。校验器新增：建筑两两 SAT 分离（≥0.6m 含出檐，门廊-书院搭接除外）、路径同岛/离岸/不穿建筑、建筑避让桥走廊、树冠避让所有民居；house≤12、path≤8、tree≤24。
- 编译器部件动态化：每栋房、每条路一个 part（`house:<id>` / `path:<id>`），可独立增量重建；文档中删除的物件其部件随增量提交一起移除。solid 与 voxel 各自实现（solid 复用 buildLibrary 盖房 + 石板实例；voxel 复用体素 buildLibrary + 路径栅格化为岛面石块）。`scene.test.mjs` 增至 10/10。
- 村庄组实验（`--set=village`）：4 个模糊意图（"安静的小渔村""高一点的山包""六七户人家路像树杈""挤一点但要过得走"），不带任何参数。mock 4/4 通过（参考解证明可行）。
- 会话模型首轮（首次输出不返工）：**3/4 通过**（含 5 户/5 户/3 户三个村庄，双后端编译 + 门廊加宽修订精确重建）。**v3 失败**：为"六七户"新增 h6 时与早先放置的 tree-ne 占位冲突，校验器返回 `树冠与建筑 h6 相交` 的结构化诊断。按诊断把树挪 5.5 米后**返修成功**，双后端编译（16 parts）。
- 结论：(1) 语义文档 + 确定性后端的路由到村庄级（7 户 + 3 巷 + 5 树，solid 1.4 万面）依然成立，部件级增量重建在高物件数下仍然精确；(2) 模型的真实错误模式是"新增物件时忘记复检旧物件"，而结构化诊断 + 局部返修恰好是为此设计的闭环——一轮诊断即修复；(3) 模糊 prompt 下模型能自行决定数量、坐标与高程并满足全部空间约束，但没有诊断时无法保证一次全对，**校验-返修环应当是产品必选项而非可选项**。
- 证据边界不变：会话模型与约束、参考解同源；首次输出协议下成功率数字（3/4）只反映本轮，不是模型排名。

验收边界：村庄语义仍限于"临水建筑群"（恰好一个书院/门廊/桥），没有商店、田地、人物;路径无连通性校验，"路像树杈"由模型自觉；未做浏览器截图验收。

## 双轨推进：渲染决策落档 + 体素斜面屋顶 + 返修环正式化

- 渲染决策写入 [ARCHITECTURE.md](../../docs/architecture/ARCHITECTURE.md)：solid 为 v1 主渲染,voxel 为第二后端 + 编辑辅助视图候选,真实模型实验后定岗。依据是用户真机截图对照：通用几何在有机形体（树、弧桥、屋顶坡面）、室内细节上明显占先,且村庄规模三角面约为体素一半。

- 返修环正式化：runner 增加"诊断返修"第二轮——首次校验失败时把结构化诊断喂回模型修一次（真实模式走 EDIT prompt,离线模式读 `<id>.repair.json`）。村庄组结果：**首过 3 + 返修救回 1 = 4/4**,修订全部精确重建 `porch`。连带发现并修复夹具一致性问题（v3 的修订输出须从返修后的文档派生,否则继承旧错误）。
- 浏览器截图对比确认：v1/v3 的体素屋顶已与通用几何几乎同形,差距集中到树木、岸线、桥栏杆。

验收边界：斜面单元目前只用于屋顶（沿 x 轴单坡）,岸线/树木未动;返修环在离线模式下只验证了管道,真实模型的返修成功率仍待 key 接入后测量。

## 子 agent 真实生成实验：首过 4/10,返修后 10/10,修订 8/10

2026-10-25。用 10 个全新上下文的子 agent 充当"外部生成模型"（冷启动,未见过参考解与历史）,覆盖两组意图（6 个藏书屋参数意图 + 4 个村庄模糊意图）,产出写入 `generated/subagents/`。这是第一次不依赖会话模型自身的外部模型实验。

**生成**：首过 **4/10**。失败模式两类：
- **schema 沟通缺口（3 例）**：模型自发给 library 加了 left/right/back 墙的窗户,而子集只支持 front。提示词只说了"入口只支持 front",没说窗户;模型的行为其实是合理外推。产品结论:光靠自然语言提示不够,contract 层的 JSON Schema（枚举墙向）或验收时的容错归一化是必需品。
- **空间计算错（3 例）**：树/建筑出岛(树冠余量按名义半径而非收缩半径算、房子只看了自身没看全局)。
**返修环**：6 例诊断返修,**4 例一轮救回,2 例两轮救回,合计 10/10 双后端编译通过**。两轮的根因是错误级联：修好窗口字段后,被短路的空间校验继续暴露第二处问题;修树出岛时挪进岛内又撞了建筑。结论:**返修环必须按"预算内多轮"设计,单轮返修不够**;诊断信息(带 nodeId/requirementId)足以让模型每轮只做定向修改。
**修订**：10 个"把门廊加宽 1.2 米"修订,**8 个精确成功**(rebuilt 恰为 porch、零越界重建),**2 个真实失败**:rotated-cove 门廊加宽后伸入桥走廊(修订提示没提桥约束);v1-quayside 门廊加宽占用了已有路径的空间(path 穿建筑)。结论:**局部修订同样需要全量重校验 + 返修环**,不能只校验被改的对象。

管道侧发现:子 agent 会给文档起自己的 id(提示没规定),离线客户端按 doc.id 查修订文件导致失配——已修(按 intent.id 查);真实产品中修订作用于内存对象,不受影响,但 contract 应考虑是否固定 doc.id。

验收边界:子 agent 与会话模型同源(GLM 系),不是跨厂商样本;每组意图样本量 4–6,数字只反映本轮;修订指令只有一种;窗户类失败可能随 prompt 微调消失,不构成对模型的排名。

## 并行双线:角色进 3D 子集 + M0 契约草案

- **支线(契约)**:子 agent 起草 [CONTRACT-DRAFT.md](../../docs/architecture/CONTRACT-DRAFT.md)(约 300 行):13 个核心类型 + 7 个 DTO + SSE 联合类型、Op/Plan/EditProposal 的 2020-12 JSON Schema、9 个 fixtures 清单、10 条开放问题、与 ARCHITECTURE.md §4 的差异表。关键判断:LogEntry(不含 world 的 Revision 投影)必须进 contract;Op.valueJson 建议改 `value?: Json`;Entity.kind 保持开放 string + 枚举表。
